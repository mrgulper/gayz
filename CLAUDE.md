# GayZ project notes

Browser Three.js zombie-survival FPS. Vite build, no framework. Verification is done by driving the real running game (Playwright, real game methods via `page.evaluate()`, not simulated input events) — both as a small committed suite and as one-off scripts.

**Tests + CI**: `tests/*.spec.js` is a committed Playwright suite (`npm test`, config in `playwright.config.js` - builds and runs against `vite preview` on port 4173, one worker, 120s per-test timeout, since each test constructs a real `Game()`). `.github/workflows/ci.yml` runs `npm run lint` → `npm run build` → `npm test` on every push/PR to `main`. The suite is narrow (build mode, construction, progression, save, settings) - it catches "the game no longer boots/saves", not feature-level regressions, so feature work still needs its own targeted Playwright check. Run it locally with `CI=1 npx playwright test` (without `CI`, `reuseExistingServer` will silently test whatever stale preview server is already on 4173). `tests/helpers.js`'s `hideAssetLoader` is a harmless no-op now (`#asset-loader` is gone, see Gotchas).

**`Game.js` split (in progress)**: `Game.js` is ~13.8k lines (was ~26.6k before the old Map 1 was deleted); self-contained UI systems are being moved out into their own modules one slice at a time. Convention (same as `CloudSaveUI.js`/`MenuPresets.js`/`MenuEasterEggs.js`): plain exported functions taking `game` as an explicit first parameter (not a class, not a prototype mixin), called as `Module.fn(this, ...)` from `Game.js`; all state stays on the `Game` instance (`game._chatChannel` etc.), so nothing else that reads it has to change. Helpers the module needs from `Game.js` (`_escapeHtml`, `_censorText`, `saveSettings`, ...) are `export`ed from `Game.js` and imported back - the circular import is fine because they're only called at run time, never at module-evaluation time. Done so far: `CloudSaveUI.js` (Cloud Save panel), `ChatUI.js` (both chat surfaces + emoji picker + mute list). Good next candidates: the Online Features cascade (`_renderCloudOnlineSection` and everything it calls), the spotlight ticker, the Clan section (`_bindClanSection`), Settings panel binders. Do each slice as a pure move (mechanical `this.`→`game.` rewrite, no behavior changes mixed in), check every caller with a grep across `src/` (not just `Game.js` - `CloudSaveUI.js` calls into chat, `style.css` comments reference method names), and verify with lint + build + `npm test` + a targeted Playwright check of the moved feature.

**`3D_ASSET_OVERHAUL.md` (repo root)** holds a complete, adversarially-verified research handoff + phased plan for replacing all ~75 procedural models with real 3D assets at zero cost (CC0 packs / free tiers / Blender scripting). Self-contained — read it before starting any asset/visual-overhaul work.

**`docs/PERFORMANCE.md`** holds the measured diagnosis of the FPS bottleneck that `QualitySettings.js` was written around while it was "still unresolved" — it is resolved: the game is CPU-bound on scene-graph traversal (14,792 objects, 470 draw calls for 35k triangles), not GPU-bound, which is why lowering resolution and quality settings never helped. Self-contained, includes a reproducible measurement script and a full A/B/C implementation plan. **Read it before touching anything performance-related, and before flipping `LOW_QUALITY_MODE`.**

**Cloud Save (`src/game/CloudSync.js`)**: Firebase Authentication (Google Sign-In) + Firestore — still no custom backend of our own, just Firebase's hosted services, and the `firebase` npm package is a real (non-dev) dependency now that it ships in the bundle. **Not** the original design: a first pass used raw Google Identity Services + Drive's `appDataFolder`, but that meant sending the project owner through Google Cloud Console's separate "Try Google Cloud for free" onboarding wizard (`console.cloud.google.com/freetrial/...`) to even reach the OAuth/API screens — a `$300 in free credit, 90 days` promo (not an actual charge, but confusing, and Step 2 of that wizard pushes phone/card verification) gated behind a product we didn't actually need. Firebase Console (`console.firebase.google.com`) reaches the same OAuth-client-creation + API-enablement outcome without that wall — its free "Spark" plan needs no billing account at all, and enabling the Google sign-in provider in Firebase Authentication auto-configures the underlying OAuth client for you (no manual consent-screen wizard). Lesson: when a Google Cloud Console flow demands billing/trial signup for something that should be free, check whether Firebase reaches the same product (Auth, Firestore, Functions are all still "Google Cloud" underneath) through its own console first, rather than pushing through the trial wall. The save blob synced to Firestore is the exact same `{localStorageKey: stringValue}` shape `_exportSave()`/`_importSaveFile()` already used for manual file-based sharing (`_snapshotLocalSave()`/`_applyImportedSaveData()` in `Game.js` are the shared helpers both paths call) — same untrusted-data handling applies (see the XSS note below), same reasoning: don't invent a second save format. `FIREBASE_CONFIG` in `CloudSync.js` holds the real `gayz-aa69c` project's config (not a secret — Firebase's web config only says which project to talk to; real security is `FIRESTORE_SECURITY_RULES`, exported from that same file, pasted into Firebase Console's Firestore Rules tab — without it every player's save would be world-readable/writable). `CloudSync.isConfigured()` gates the UI (disabled Sign In button + explanatory copy) for a fresh clone/fork that hasn't set up its own Firebase project yet.

**Gotcha**: `signInWithPopup` opening a blank/white popup that closes itself within about a second, with no error shown on-page, is `auth/unauthorized-domain` — Firebase auto-authorizes `localhost` and the project's own `*.firebaseapp.com` domain, but NOT a custom deployed domain. Fix: Firebase Console → Authentication → "Settings" tab (not "Sign-in method") → "Authorized domains" → Add domain → the real deployed hostname (e.g. `gayz.vercel.app`). Needed once per hostname the app is ever served from (would need re-adding if the domain ever changes).

**Online Features (leaderboard/weekly ranking/friend compare/global kill counter/community poll)**: layered on top of Cloud Save once Firestore already existed — same "extend the existing backend, don't invent a new one" reasoning as everything else in this section. Four new collections beyond `saves/{uid}`, all added to `FIRESTORE_SECURITY_RULES` in `CloudSync.js` (this is the FULL ruleset now, not additive — re-publishing it replaces whatever's currently live in Firebase Console, so always paste the whole exported string, never just a diff): `leaderboard/{uid}` (public read, own-uid write with type/range bounds - also doubles as the friend-compare lookup by nickname, no separate friends system needed), `weeklyLeaderboard/{week}/entries/{uid}` (same shape, fresh sub-collection per week so old weeks' rankings survive), `stats/global` (single doc, public read, signed-in-only `increment`-only write capped per call - **must be created once by hand** via Firestore Console's "Start collection" UI with a `totalKills` field set to `0`, since the rules deliberately block client-side `create` on it), and `polls/{pollId}/votes/{uid}` (one vote doc per account, `allow create` with no `update`/`delete` is what actually enforces one-vote-per-account - results read via a `getCountFromServer` aggregation query per option, never by downloading every vote doc). The one hardcoded poll (`POLL_ID`/`POLL_OPTIONS` in `Game.js`) is developer-authored content, not user-generated, so there's no moderation surface beyond picking a new `POLL_ID` for the next one (a new ID starts vote counts fresh rather than resetting the old poll's tally).

A follow-up round added: a **Global Rank badge** (`CloudSync.fetchMyGlobalRank` - a `getCountFromServer` count of leaderboard docs with a strictly better `bestNight`, +1 - appended to `#menu-player-tag` via the new `_renderPlayerTag()`, which replaced two duplicate inline call sites), a **nearest-rival nudge** (`fetchNearestRivalAbove` - same field, opposite direction, `limit(1)`), a **saved friends list** (`settings.savedFriends`, capped at 5, reuses the same leaderboard-by-name lookup the Friend Compare box already had), a **weekly-reset countdown** folded into the existing spotlight ticker's weekly-challenge mode (`_daysUntilWeekReset()` - deliberately doesn't re-derive the ISO-week math by hand; it feeds future dates back through `_thisWeekStr()` itself so it can never drift out of sync with what "this week" means elsewhere), a **login-streak calendar** (`loginStreak.recentDates`, a capped-at-7 rolling array added alongside the existing `streak` counter, not a replacement for it), an **anniversary line** (`careerStats.firstPlayedDate`, set once on the very first completed run, never touched again), and a **mutator-exploration nudge** as a 5th spotlight mode (`settings.mutatorsEverEnabled`, recorded in ONE place — the Play button's click handler, where every mutator flag is already read for real — rather than editing all ~15 individual mutator checkboxes; deliberately excludes `dailyChallenge` since that's a distinct system already promoted via its own daily-reset spotlight mode, not a "try this mutator" pick). `MUTATOR_LABEL_KEYS` (`Game.js`) was renamed/extended from the older `WEEKLY_FEATURED_MUTATOR_LABEL_KEYS` (which only covered the 8 `WEEKLY_FEATURED_MUTATORS`) to cover all 14 non-daily mutators, rather than adding a second near-duplicate label map. Also fixed a real duplicate-audit catch mid-build: the Nearly There nudge was asked to show "top 3" closest achievements, but this codebase only has 2 achievements with genuinely persistent numeric backing (`NEARLY_THERE_CANDIDATES`, see its own comment) — everything else is a per-run counter that resets, so showing "progress" toward those would be actively misleading. Shipped showing however many honestly qualify (0-2) rather than padding to a number that doesn't reflect what's actually trackable.

A third round (round 4) added, after auditing for and deliberately skipping the riskier asks (mid-run save/resume, server-side anti-cheat, a social-infra bundle of friend-challenges/clans/activity-feed/presence, and chat/messaging - all flagged as needing real new cost/scope/moderation before building): **achievement unlock hints** (`hintKey` field added to every `ACHIEVEMENTS` entry, shown in the Achievements panel instead of a bare `"???"`), a **region filter** on the leaderboard (`settings.region`, one of 6 values, `region` field on leaderboard docs is *omitted entirely* when unset rather than defaulted to a region - the security rule's enum check only applies when the field is present at all), an **achievement-count leaderboard** (same `leaderboard` collection, new `achievementCount` field, sorted differently - not a separate collection), a **global average comparison** and **percentile ranking** (both via Firestore's `getCountFromServer`/`getAggregateFromServer` aggregations, never a client-side download-and-average), a **live-subscribed leaderboard** (`CloudSync.subscribeTopLeaderboard`/`onSnapshot`, subscribed only while the Cloud Save panel is actually open and unsubscribed on close/sign-out to keep the read cost bounded), a **"Most Improved" badge** (just a label on the weekly leaderboard's #1 entry - that ranking already *is* "most improved this week" by the same measure, no new metric needed), **"Today" session stats** (`_sessionKills`/`_sessionStartTime`, deliberately session-local only, reset every page load, never persisted - distinct from careerStats' lifetime totals), a **Best Run breakdown card** and **favorite-difficulty line** (both pure-derived from data already tracked - `runHistory`'s difficulty/loadout/companion fields and `careerStats.difficultyStats`, no new tracking), **avatar frame tiers** (automatic border-color escalation off the same 1-5 tier index the avatar-level badge already computes, not a picker), a **custom Player Title color** (`settings.titleColor`, applied via `style.setProperty('color', ..., 'important')` since `.menu-best-stats`'s own color rule is itself `!important`), a **detailed Achievement Showcase style** (stacks the 3 slots into a column of two-line cards instead of the compact row, since 3 full achievement names side by side would overflow the 290px right column), a **companion color preview swatch**, **Large Text Mode** (CSS `zoom` scoped to `#menu` + every modal panel - *not* a root `font-size` bump, since almost all sizing here is fixed px, not rem; deliberately does not touch in-game HUD text, which already has its own HUD Scale slider for exactly that), **High Contrast Mode** (a `filter: contrast()/saturate()` on `#app`, works during gameplay too), a persistent **Keybind Cheat Sheet** HUD toggle (distinct from the one-time tutorial toasts and the replayable How to Play modal), **sound test buttons** next to the volume sliders, a **structured, dated changelog list** in Credits (replacing the old single static paragraph), and **standalone trivia facts** as a 6th spotlight mode (distinct from `SPOTLIGHT_TIPS` - actionable advice vs. pure lore flavor).

**Gotcha**: a single `getAggregateFromServer(coll, { avgKills: average('bestKills'), avgNight: average('bestNight') })` call - averaging two different fields in one aggregate query - triggered `failed-precondition: The query requires an index`. Splitting it into two separate single-field aggregate calls (`Promise.all([...average('bestKills')..., ...average('bestNight')...])`) needs no index at all and returns the same data. If a future aggregate query ever demands an index, try splitting fields into separate calls before assuming a Firestore Console index (or a paid-plan limitation) is actually required - it often isn't.

**Chat** (2026-08-27) - the "chat/messaging" item flagged as skipped above eventually got built, once moderation was actually decided (no word filter, client-side spam mute only - see the design conversation). Splits across **two completely different transports**, which matters for anyone touching it: Global chat (`globalChat/{messageId}`) and Clan chat (`clans/{clanId}/messages/{messageId}`) are plain Firestore collections, same pattern as everything else (`CloudSync.sendGlobalChatMessage`/`subscribeGlobalChat`, `sendClanChatMessage`/`subscribeClanChat` - `onSnapshot`, capped history, subscribed only while the chat panel is actually open). **Party chat is not Firestore at all** - a multiplayer session's players aren't Firebase-Auth-signed-in (see the Realtime Database section above - `Multiplayer.js`/`api/multiplayer/*.js` mint their own random `playerId`, no Firebase Auth involved), so party messages piggyback on the existing 100ms position-sync poll (`api/multiplayer/sync.js`'s `chatText`/`chatNickname` request fields, `chat` response field) instead - same broadcast-and-TTL-prune shape as `worldEvents` in that file, just a 10-minute TTL instead of 15 seconds since chat is meant to read as real scrollback, not a one-shot trigger. The client dedupes party messages by id (`_chatPartySeenIds`) the same way it already dedupes world events. Rate-limiting (5+ messages in 10s → 5-minute mute) is enforced **client-side only** in all three channels - there's no custom backend here to enforce it server-side (same trust model as everything else, see the anti-cheat note above), so a modified client could bypass it; the Firestore security rules only enforce message shape/length, not timing. The keydown-suppression-while-typing fix (letters typed into the chat input no longer also trigger gameplay hotkeys) reused the exact capture-phase `stopImmediatePropagation()` technique documented in the Menu redesign notes below for the mouse-parallax fix - same reasoning, different listener.

## Standing rules for this project

- Every completed update gets committed, pushed to GitHub (`mrgulper/gayz`, private), and deployed to Vercel production (`npx vercel --prod --yes` → `gayz.vercel.app`) without asking each time.
- **Panel URLs need no per-route setup (2026-10-01).** `vercel.json` has ONE catch-all rewrite (`/((?!api/).*)` -> `/index.html`; Vercel serves real files first, so assets are unaffected). It used to list every panel path by hand (`/store`, `/inventory`...), and every new panel added to `_bindPanelRouting` without a matching line 404'd on refresh (reported on `/market`). Don't go back to a per-route list.
- **Never leak the owner's GitHub username or AI/tooling names to the public Discord `#updates` feed** (2026-09-30 report). `.github/workflows/discord-update-notify.yml` posts every push to `main`; it used to post the raw first line, which for a merged PR is GitHub's `Merge pull request #N from <username>/claude/<branch>`. It now posts the PR title instead, skips branch-sync merges, and scrubs `mrgulper`/`gulper`/`claude`/`anthropic` words - don't undo that. On top of it: PR titles and commit titles are player-facing patch notes (plain description of the change, no username, no "Claude"/"AI"), and when merging a PR set the merge commit title to the PR title itself (`commit_title`) rather than GitHub's default.
- For batched/greenlit feature work, build straight through without stopping for confirmation checkpoints between items.
- **Every search bar looks like the Settings search (standing rule, 2026-10-01).** Give any new search input `class="nickname-input search-bar"` (dark fill, thin gold border, pill shape, centered on its own line - see `.search-bar` in `style.css`) and only override width/margin per box, never the colors/border/shape. All existing ones (Settings, Achievements, GayZ Features, Inventory skins, emoji picker, Market) already use it. Since 2026-10-02 the same oval shape also goes on text boxes and dropdowns next to them (chat boxes, Add a Friend, Status picker, Achievements Category/Sort, clan invite - pill block at the end of `style.css`): give any new input/dropdown `border-radius: 999px` too.
- **Map-making rules (standing, 2026-10-01 - Gaymi's feedback on Map 3).** Any generated or hand-built map (`Map3Generator.js` and any future one): (1) use only block types that already exist in `BLOCK_TYPES`; (2) not "squared" - never one identical box per lot lined up in rows: split blocks into several buildings of different widths, depths, heights and setbacks, mix shapes (L, U, notched, setback towers, pitched roofs), leave alleys/yards between them, and scatter trees/lamps/props off-grid; (3) close the map in with a natural-looking ring of buildings along the edge (uneven heights, different materials, a barricade and wrecked car where roads run into it), plus a ragged rock wall on every border cell the ring leaves open (tallest at the edge, lower inward) - no spot may show empty sky or let a Try Map player walk out; (4) never leave a hole under water/lava - every liquid cell gets a solid bottom and solid sides so nothing falls through; (5) ladders always have a wall or support right behind them and stay indoors - on a tower that steps in higher up, put the ladder inside the TOP tier (with a support column below the step), and drop any ladder left with nothing beside it after ruin holes are carved (reported 2026-10-01: ladders "hanging on nowhere"); (6) sloped roofs only on plain, whole rectangles, rising half a block per cell (slab, full block, slab...) - full-block steps on L-shapes read as a messy staircase; (7) **no ruined buildings at all** - ragged tops, blown-out holes and smashed windows all read as "broken" to Gaymi (reported twice); keep every building whole; (8) **no street grid** - from the top-down view an even grid of equal square blocks reads as "16x16"; use winding/bent/diagonal roads, uneven spacing, roads that end in T-junctions and a roundabout, so blocks come out in different sizes and shapes (Map 3 does this with road polylines + a distance field, then flood-fills the land into blocks and cuts every building's footprint to its block - `building(box, style, facade, mask)`); (9) **every building can be entered and climbed to the top** (reported 2026-10-02: tall buildings had no way up): each gets a door on a straight stretch of wall whose inside is a real room and whose outside is open (`SIDES` search in `building()`, facade side first), a half-block step outside it (the ground floor is a block above the street), and a ladder through every floor and, on flat roofs, through a roof hatch - or (2026-10-03, "not all ladders") a real staircase instead in about half the buildings (`findStairwell`/`buildStairs` in `Map3Generator.js`: a 6x2 strip along an inside wall, flights going back and forth between its two lanes, stairs of the building's floor material facing the climb, three cells of headroom over every stair - two wasn't enough to step up - and the 2-high ground floor's ceiling opened in front of the first stair; chosen by its own seed, and the furniture/roof-clutter picks that skip the stairwell still draw their random number, so the rest of the city is unchanged); nothing may stand in the doorway or in front of the ladder (props are kept clear, a building clears its lot first so earlier trees don't end up inside, trees never grow through anything, low leaves in front of a door are trimmed, a door left facing a later neighbor's wall gets a second door through it, edge-ring buildings never overlap at corners, setback towers only where the top tier still has a room); (10) check automatically that every ladder has a wall beside it, every water cell has a solid bottom and sides, and every building's top is reachable from the street (a walking flood-fill over the generated blocks - 73/73 on the current seed), then verify by flying the editor camera around it (overview + street level + close-ups of houses/towers) and looking, not just by counting blocks.
- **Patch Notes must always be updated with the game (standing rule, 2026-10-04).** Every player-facing update adds its bullets to the newest entry in `#changelog-list` (a new `vX.YY · Mon D, YYYY` entry for a new day) in the same change - it's hand-written HTML like GayZ Features, and it silently stopped at v0.06 (Sep 29) for five days of updates until Gaymi noticed; v0.07-v0.11 were back-filled from the git history.
- **Patch notes format (What's New, `#changelog-list` in `index.html`, 2026-10-02).** Each entry is `<div class="changelog-entry"><span class="changelog-date">vX.YY · Mon D, YYYY</span><div class="changelog-text">` + one `<div class="changelog-group changelog-added|changelog-changed|changelog-fixed"><span class="changelog-group-label">Added|Changed|Fixed</span><ul><li>...</li></ul></div>` per kind that has items (in that order) + `</div></div>` - one short bullet per change, never one long paragraph (Gaymi: "everything jammed up"). The panel heading is "Patch Notes" (`buildVersionLine`). Removals go under Changed.
- **The Map Editor picker** has the oval search bar and a block-type dropdown beside it, inside the picker's frame (`PICKER_CATEGORIES`/`_blockCategory` in `BuildMode.js`: Special first - just the Invisible Block for now, and Special blocks also lead the All list via `PICKER_TYPES_SORTED` - then Wood, Stone, Ores & Metals, ..., Slabs, Stairs, Doors/Fences/Ladders). A new block lands in a category by its id; check it isn't in the wrong one. Stairs icons are drawn as stairs (`stairsIconURL` in `BlockTextures.js`).
- **Every block gets a slab AND stairs (standing rule, 2026-10-03).** Any new full block added to `BLOCK_TYPES` (`BuildMode.js`) automatically gets `${id}slab` and `${id}stairs` from the two generator loops right after the list (`slabOf`/`stairsOf` = source id, textured from it via `_shapedSource`) - don't skip them or add a block in a way that bypasses those loops (only water/lava and the hand-named slab/stairs sources are left out). Give every new block its own painter in `BlockTextures.js`'s `BY_ID` (or a matching regex fallback like `terracotta$`/`stainedglass$`) rather than the generic pattern fallback. Stairs face the way you look when placed, like Minecraft (`_stairFacing`, 0 +z / 1 +x / 2 -z / 3 -x, the side the high step is on; saved as `facing` only when non-zero - riding the slot format's door list - so old stairs load as 0; carried in undo `state`).
- **Hand-written player pages are enforced, not remembered (2026-10-04, root-cause fix after both GayZ Features and Patch Notes silently fell days behind).** `scripts/check-docs.mjs` runs as a git `commit-msg` hook (`.githooks/`, wired up by `npm install`'s `prepare` -> `scripts/install-hooks.mjs` setting `core.hooksPath`) and as a CI step on every PR: any commit touching `src/`, `public/` or `index.html` must also edit Patch Notes (`#changelog-list`) **and** GayZ Features (`#features-main`) - both regions end in an `<!-- end ... (scripts/check-docs.mjs) -->` comment the script looks for, keep them - or carry `[no-notes: <why>]` / `[no-features: <why>]` in the commit message **body** (never the title, which goes to Discord). The reason is required (a bare `[no-notes]` fails) so a skip is a written decision someone can question; no script can judge whether the reason or the page's wording is actually right, so still read the entry you're touching. Don't bypass with `--no-verify`. **Nothing countable is typed into GayZ Features by hand:** heading counts are `<span data-feature-count="key">` (`_featureCounts()`), numbers inside descriptions are `<span data-feature-value="key">` (`_featureValues()` - mastery kills, crate prices, timers, the grapple key, languages...), and the expandable lists are **built entirely from code** by `_syncFeatureLists()` from `_featureCatalogs()`: each entry's name and one-line description live next to the thing itself - `about` on `WEAPONS`/`MELEE_VARIANTS` (`WeaponSystem.js`), `ZOMBIE_TYPES`, `NIGHT_EVENTS` (with `name`), `ITEM_INFO` in `Inventory.js`, `MUTATOR_INFO`/`GAME_MODE_INFO` in `Game.js` (`about` may be a function when it names a game constant) - so a new weapon/zombie/item/mutator shows up automatically and one without a description fails the test (`data-missing`). Only `data-extra` items with no single thing in code (Weekly Featured Mutator) are typed in `index.html`. `check-docs.mjs` fails on any digit left in `#features-main` outside those spans (names like AK-47 or Map 3 go in its `ALLOWED_NUMBERS`; `node scripts/check-docs.mjs --page` checks just that), and `tests/docs.spec.js` fails on any `data-auto`/hidden list item, an unknown value/count key, an unfilled `{placeholder}` in How to Play, a rebound key not showing up in text, and any Map Editor pause-screen shortcut (`BuildMode.MENU_SHORTCUTS`) that doesn't do its job when pressed - a new shortcut needs an entry in that test's `CHECKS`.
- **Hand-written sentences are tied to the code they describe (2026-10-04).** A script can't tell whether a sentence is still true, but it can tell when the code behind it changed: every live GayZ Features entry has `data-code="identifiers"` (functions/constants that implement it), and each How to Play step (`HOWTOPLAY_STEPS`, Game.js) and Map Editor pause tip (`MENU_TIPS`, BuildMode.js) has `code: '...'`. `check-docs.mjs` fails when a change adds/removes a non-comment line using one of those identifiers without editing that text in the same change - name it with `[reread: <entry title or text key>]` in the commit message after actually re-reading it. It also fails on a live entry with no `data-code` and on a linked identifier that no longer exists in `src/` (removed or renamed - fix the text and the link). Pick distinctive identifiers (a constant or function used only by that feature), not ones every commit touches. `code: ''` is allowed for text with no gameplay behind it (htpRules). The typed-key check also covers wordings like "hit F", "the F key", "tecla F", "按F键", `[F]`, `<kbd>` (letters stay case-sensitive so "needs a key" isn't flagged), and scans string literals in code, not only i18n.js.
- **No key letter is ever typed into player text (2026-10-04).** Every string names keys as `{key:<id>}` (`**{key:interact}**`, `{key:healthPack}`, `{key:move}` for all four movement keys) and `i18n.js`'s `interpolate` fills in the player's real key through the lookup `Keybinds.js` registers (`setKeyNameLookup`): a rebindable `ACTIONS` id, a `HOTBAR_ITEM_SLOTS` id, or a `FIXED_KEYS` id (non-rebindable keys - inventory Tab, the Map Editor's T/M/V - which the handlers also read, so text and behavior can't differ). This replaced ~240 typed letters across all languages after "press H to use" outlived the move of Health Packs to hotbar slot 4, and the upgrade machine/mystery box said "Press E" for an F action. `check-docs.mjs` fails on a typed key in en/zh/hi/es text and on a `{key:...}` id Keybinds.js doesn't know.

The Live/Coming Soon numbers count `.feature` elements automatically.
- Don't ship inert UI. If a feature's markup/CSS is scaffolded before its logic is wired up, leave it uncommitted rather than deploying a checkbox or HUD element that does nothing.
- **Every new i18n key must ship translated into `zh`, `hi`, and `es`, in the same change that adds it to `en`.** (Narrowed 2026-09-11 - only English/Mandarin Chinese/Hindi/Spanish are called properly supported now; every other language shows a "Coming soon" tag in Settings > Language and is intentionally left on whatever it last had, English-fallback included, until it gets promoted to supported. ## Recurring bug classes

- **Shared-material mutation**: runtime flash/recolor effects (barrels, targets, hit-flash, etc.) must `.clone()` their material per instance. A shared module-level material fought over by simultaneous instances is a recurring source of visual bugs in this codebase.
- **Rotated-mesh AABB inflation**: `THREE.Box3.setFromObject()` on a rotated mesh inflates well past its visual footprint. Build axis-aligned collider boxes explicitly from known dimensions instead, for anything not axis-aligned.
- **Shared single-element toasts silently clobber each other.** `loreToast`/`companionBarkEl`/`achievementToast`/etc. are each one shared DOM element re-triggered via `classList.remove('show'); void el.offsetWidth; classList.add('show')` — if two calls to the same toast happen in the same synchronous tick (or before the CSS animation finishes), the first is silently skipped, never shown. Usually an accepted tradeoff for flavor/lore toasts, but worth a real queue (see `_achievementToastQueue`/`_drainAchievementToastQueue` in `Game.js`) for anything rare/precious enough that losing one matters — achievement unlocks got this fix after the completionist auto-cascade could unlock two achievements in one tick. Also check new fixed-position HUD elements (toasts, feeds, badges) against each other's screen coordinates — `#kill-feed` and `#achievement-toast` shipped at the same `top-right` slot until caught.
- **Never `scene.add()`/`scene.remove()` (or `.visible = true/false`) a `THREE.Light` at runtime.** three.js bakes the number of visible lights into every material's compiled shader, so adding/removing/toggling one recompiles everything (150-600ms, ~2.9s on a weak GPU - a real "randomly 0fps" report, 2026-09-19). The old Map 1 needed a fixed light pool and light proxies for this (both deleted with it, 2026-10-06); the Map Editor and the block city simply have no point lights (glow is baked vertex light, see the chunk-mesh note). Keep it that way.
- **A single mutable `this.X` state object (not an array-based one) can go null partway through the very function that's using it, if that function calls something that clears it.** `_updateAirdrop()`'s outer `if (this.airdrop) { ... }` guard was checked once at the top, but the claim branch inside it called `_claimAirdrop()`, which sets `this.airdrop = null` as one of its last steps - a line further down in that *same* outer block then read `this.airdrop.beam` unconditionally, crashing with a null-property read on every single successful pickup, from inside the per-frame tick loop (an uncaught exception there stops `requestAnimationFrame` from ever rescheduling, freezing the whole game - real report, 2026-09-21). Audited every other `_acquireFxLight`/`_releaseFxLight` consumer (`Pickups.js`, `WeaponSystem.js`'s Void Ripper orb, `ZombieManager.js`'s golden halo, hazard zones) for the same shape and found none - they're all either array-based with `.filter()`/`return false` or `.splice()` right at the end of the block (removing a *local* loop item, not a shared property, and nothing reads it again after), or a `setTimeout` closure over a local `const`. The airdrop bug specifically needed a *singular*, non-array, per-tick-updated state property whose own "claim/expire" function nulls it out **without returning/exiting** the caller's block immediately after. When writing a new singular (not array) stateful system with its own per-tick update + claim/expire function: either have the claim/expire function's caller `return`/`continue` right after calling it, or re-check the property (not just re-check a field on it) before any further access in the same block.
- **GLB texture resolution is a memory budget, not a quality knob - keep weapon/prop textures at 256x256.** Every embedded texture is decoded to a full uncompressed bitmap (width x height x 4 bytes, plus ~33% for mipmaps on the GPU) no matter how small the PNG inside the file is. The weapon pack shipped 91 textures at 1024x1024 (most of them near-flat colors only 14-48 KB as PNGs, but 5.6 MB each once decoded), and several guns embed their own copies of the same images - about 1 GB of estimated texture memory before the player even pressed Play, which is what crashed iPhones and school Chromebooks on the homepage (2026-09-28 report). Fixed by resizing every weapon/prop GLB's textures to 256 (`npx @gltf-transform/cli resize in.glb out.glb --width 256 --height 256`): ~1,011 MB -> 133 MB. Any new GLB added to `public/models/` should go through the same resize before committing, and check `inspect`'s gpuSize column rather than the file size.
- **Map 1 performance (2026-10-06, "20-50fps on my old phone").** Measured first: from a street the city drew up to ~300 draws / 250k triangles, a full zombie wave added ~130 draws (8 meshes each), and the real killer was the zombie flow field - one `_rebuildFlow` pass took ~65ms on a fast PC (several hundred ms on a phone) and ran every 0.5s plus on every cell the player stepped into, i.e. a freeze twice a second. Fixes: the flow field now runs as a time-sliced job (`_startFlow`/`_stepFlow`, `FLOW_BUDGET_MS` per frame, zombies follow the last finished field; numeric `cellKey` keys and a per-pass `_memo` of cell solidity); zombies are drawn as one `InstancedMesh` per body part (`_zombieBatch`/`drawZombies`, called from `BuildMode.render()`; each zombie keeps a cloned body only for its part matrices, hit flash is `instanceColor`, `_removeZombie` must not dispose the shared geometry); **View Distance** (Settings > Graphics, `settings.viewDistance`, `VIEW_DISTANCES` in BuildMode.js) hides chunks past it (`BlockChunks.cullTo`, nearest-edge distance, never the camera far plane - the night stars sit 150 units out) with `scene.fog` (always present so it never recompiles shaders) colored from the sky every frame; Auto starts at Max on a computer and Medium on touch devices (`TOUCH_DEVICE`) and Auto Quality steps it down once resolution is already at its floor (`stepAutoView`, given back first when there's headroom); camp NPCs past it are hidden; leaves are a `cutout` chunk kind (alpha-tested, depth-writing) instead of blended; touch devices get anisotropy 1. - **Cloud Save is a three-way merge, not an upload (since 2026-09-28).** `CloudSaveUI.syncWithCloud` reads the cloud, merges it with this device's data against `localStorage['gayz-cloud-base']` (the content this device last agreed with the cloud on) using `CloudMerge.mergeSaves`, and uploads with a Firestore compare-and-set transaction (`CloudSync.pushCloudSaveIfUnchanged`) - never a blind `setDoc` over the save. Any *other* Firestore read added to a sign-in/restore-type flow needs the same three-way handling (success / confirmed-empty / failed-with-retries-exhausted), not a bare `if (!result)` that conflates the last two.

## Playwright verification quirks (apply to both the committed suite and one-off scripts)

- Separate `page.evaluate()` calls can have multi-second real wall-clock gaps even for trivial scripts. Timing-sensitive assertions must happen inside one `evaluate()` call.
- `THREE` isn't globally exposed in the bundled build — `new THREE.Vector3()` inside `page.evaluate()` fails. Clone an existing Vector3 already in scope instead.
- Moving a mesh via `.position.set()` post-construction doesn't update `matrixWorld` until the next `renderer.render()`. Call `mesh.updateWorldMatrix(true, false)` before raycasting against a repositioned mesh.
- Fake zombie/rival test stubs need a `hittableMeshes: []` field or `WeaponSystem._fire()`'s `flatMap` throws.
- `Game.js`'s constructor sets `window.__game = this` at the very end, specifically so Playwright can drive real game methods without reaching into module scope — use `page.waitForFunction(() => window.__game)` to know the game finished constructing before calling anything on it.
- Headless Playwright can't actually grant real Pointer Lock (`THREE.PointerLockControls: Unable to use Pointer Lock API`) — the `lock`/`unlock` events this game relies on for pause-menu/audio state never fire from a real `.lock()` call in that environment. Set `game.gameStarted = true` (and whatever other flag the test needs) directly instead of assuming a `playBtn.click()` produced real lock state.
- Raycasting against a zombie (a `SkinnedMesh`) returns zero hits until `game.renderer.render(game.scene, game.camera)` has actually run at least once — `SkinnedMesh.raycast()` lazily computes its own world-space bounding sphere from live bone transforms, which are only ever baked by the renderer's normal per-frame `skeleton.update()`. Spawning a zombie and immediately calling `WeaponSystem._fire()`/a manual raycast in the same `evaluate()` silently misses every time; call `renderer.render(...)` once after positioning everything and before the raycast. Also don't aim at eye-height (~1.6) — this game's zombie mesh's own vertical extent is only about ±1 around its group origin, not a human eye-height collider.
- A synthetic event dispatched via `window.dispatchEvent(...)` never reaches a capture-phase listener registered on `document` (e.g. `PlayerController`'s mousemove interceptor) — `window` isn't in that event's propagation path unless the target is `document` itself or one of its descendants. Dispatch on `document` (or a real in-page element) instead of `window` when testing anything that relies on a `document`-level listener.
- `window.location.reload` can't be reliably stubbed from inside `page.evaluate()` (a plain `window.location.reload = fn` reassignment silently doesn't stick in Chromium) — and unlike an earlier note here, a real `location.reload()` firing *during* an in-flight `evaluate()` call (not just before/after one) reliably throws `Execution context was destroyed, most likely because of a navigation` and kills every other check queued in that same `evaluate()` call along with it. Test any reload-triggering action (Restore Defaults, Reset Progress, Hardcore respawn, Import Save, Clear Leaderboards) in its own isolated `page`/`evaluate()` call, wrapped in try/catch for that exact error, and verify the state it wrote (localStorage contents) via a follow-up read rather than trying to catch it mid-navigation. Don't issue your own `page.goto()` right after to force a clean reconnect either — it races the app's own in-flight reload and can lose with `net::ERR_ABORTED`; a plain `page.waitForTimeout(1500)` before the follow-up read is more robust than any explicit re-navigation.
- Two full `Game` instances (each its own WebGL context + running `requestAnimationFrame` render loop) constructing simultaneously in one headless browser is *slow* under load — measured over 20s just for the second one's constructor to finish, compared to ~1-3s for the first. If a test needs a second `page` (e.g. to verify state after a reload-triggering action from the point above), `await page.close()` the first one first rather than leaving it running in the background.
- `FileReader.readAsText(file)` on a `File` built from a `Blob` in a test never fired its `onload` callback at all in one observed headless Playwright run (silently hung forever, not slow) — even though the exact same code path worked correctly via manual testing expectations. `file.text()` (the modern Promise-based `Blob`/`File` method) doesn't have this problem and is simpler besides; prefer it over `FileReader` for anything reading an uploaded file, both in game code and in tests.
- **`#asset-loader` no longer exists (removed at some point, confirmed gone 2026-09-26 - this note was stale and referenced dead markup for a while).** `main.js`'s own comment now explains why: there's no blocking full-page loading screen anymore - the homepage's static HTML/CSS paints immediately, it just isn't interactive until the model-preload `Promise.all` resolves and `new Game()` finishes constructing, same as any ordinary page. Don't `getElementById('asset-loader')` in a new test; there's nothing to hide. The real, current gate for "can I click anything yet" is `window.__game` existing, nothing else.
- `page.waitForFunction(() => window.__game, { timeout: 60000 })` has been observed reporting `Timeout 30000ms exceeded` - ignoring the explicit override - across multiple sessions now, cause still unconfirmed. A poll loop instead (`while` + `page.evaluate(() => !!window.__game)` + `page.waitForTimeout(500)`, throwing after your own deadline) sidesteps it entirely and has been reliable. Before blaming the app, also check for leftover Chromium processes from earlier crashed/never-closed test scripts (`ps aux | grep chromium`) - a build-up of dozens of them has caused a *new* page's Game construction to hang well past 60s in this same environment; `pkill -f chromium` between test batches (or whenever a run errors out before reaching `browser.close()`) keeps this from compounding.
- A macOS screenshot's filename (`Screenshot YYYY-MM-DD at H.MM.SS AM/PM.png`, saved to `~/Documents` or `~/Desktop`) uses a narrow no-break space (U+202F, not a regular space) between the time and AM/PM. A literal double-quoted path with a normal space silently fails with "No such file or directory" even though the file is right there in a directory listing - use a shell glob (`~/Documents/Screenshot*3.43.53*.png`) instead of typing the exact name. Separately, the Bash tool's default sandbox can't see files outside the project/scratchpad (e.g. `~/Documents`) at all - `dangerouslyDisableSandbox: true` is needed for a one-off `cp` to pull a user-provided image in, even once the filename issue above is fixed.
- A standalone empty (or text-only) `<span>` sibling added between existing flex-item buttons/links (e.g. a dot separator dropped between nav items) can measure as fully correct in every diagnostic - `getComputedStyle` (right color/size/opacity/display), `getBoundingClientRect` (sane on-screen coordinates), even `document.elementFromPoint` at its own center resolving back to that exact span (so nothing else is covering it) - and still never paint a visible pixel, in a `page.screenshot()` *or* a plain full-page screenshot, at any size/color including an obnoxious 20px solid red test circle. Root cause not identified (not background-clip, not a mask/blend-mode rule, not a font/glyph issue - a plain CSS `background` box hit the same wall a text character did). Reattaching the same visual as a `::after` pseudo-element on the (already correctly rendering) adjacent link itself, rather than a separate sibling node, rendered correctly on the first try. If a small decorative element between two other elements refuses to render despite every diagnostic saying it should, stop trying to fix the standalone-node version and reattach it as a pseudo-element on a neighbor instead of continuing to debug why the sibling won't paint.

Lesson for next time: a batch that adds several small elements across *multiple* columns is deceptively expensive, because `#menu-layout`'s row height is the *tallest* column, not the sum - estimate cost per-column, not per-feature, before assuming small individual additions are safe.
- Emoji were tried once for the Achievement Showcase badges (`icon: '🩸'` etc.) and reverted before shipping - `#profile-emblem-row`'s own comment in `style.css` documents a deliberate "no-emoji UI" convention (plain colored swatches instead), and a `grep` confirmed zero emoji anywhere else in the codebase. Replaced with a `tag`/`color` pair per achievement (a short monogram like `FB`/`5N` + a hex accent color) rendered as a small colored-border swatch, consistent with the emblem picker's existing visual language. Check for a codebase-wide styling convention like this (a comment on a *similar* existing element, not just a grep for the literal thing you're adding) before introducing a new visual pattern.
- `tHtml(key, params)` (`i18n.js`) is the existing convention for i18n strings that need inline `<b>` emphasis when rendered via `innerHTML` - the source string uses `**bold**` markdown-style markers (converted to `<b>` internally), not literal `<b>` tags. Used for the new How to Play walkthrough steps; writing raw `<b>` tags directly into an i18n string and rendering with plain `t()` (which does *not* HTML-escape, so it would have silently "worked") would have broken from the established pattern for no reason.
