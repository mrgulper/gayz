# GayZ project notes

Browser Three.js zombie-survival FPS. Vite build, no framework. No committed test suite — verification is done by driving the real running game (Playwright, real game methods via `page.evaluate()`, not simulated input events).

**`3D_ASSET_OVERHAUL.md` (repo root)** holds a complete, adversarially-verified research handoff + phased plan for replacing all ~75 procedural models with real 3D assets at zero cost (CC0 packs / free tiers / Blender scripting). Self-contained — read it before starting any asset/visual-overhaul work.

**Cloud Save (`src/game/CloudSync.js`)**: Firebase Authentication (Google Sign-In) + Firestore — still no custom backend of our own, just Firebase's hosted services, and the `firebase` npm package is a real (non-dev) dependency now that it ships in the bundle. **Not** the original design: a first pass used raw Google Identity Services + Drive's `appDataFolder`, but that meant sending the project owner through Google Cloud Console's separate "Try Google Cloud for free" onboarding wizard (`console.cloud.google.com/freetrial/...`) to even reach the OAuth/API screens — a `$300 in free credit, 90 days` promo (not an actual charge, but confusing, and Step 2 of that wizard pushes phone/card verification) gated behind a product we didn't actually need. Firebase Console (`console.firebase.google.com`) reaches the same OAuth-client-creation + API-enablement outcome without that wall — its free "Spark" plan needs no billing account at all, and enabling the Google sign-in provider in Firebase Authentication auto-configures the underlying OAuth client for you (no manual consent-screen wizard). Lesson: when a Google Cloud Console flow demands billing/trial signup for something that should be free, check whether Firebase reaches the same product (Auth, Firestore, Functions are all still "Google Cloud" underneath) through its own console first, rather than pushing through the trial wall. The save blob synced to Firestore is the exact same `{localStorageKey: stringValue}` shape `_exportSave()`/`_importSaveFile()` already used for manual file-based sharing (`_snapshotLocalSave()`/`_applyImportedSaveData()` in `Game.js` are the shared helpers both paths call) — same untrusted-data handling applies (see the XSS note below), same reasoning: don't invent a second save format. `FIREBASE_CONFIG` in `CloudSync.js` holds the real `gayz-aa69c` project's config (not a secret — Firebase's web config only says which project to talk to; real security is `FIRESTORE_SECURITY_RULES`, exported from that same file, pasted into Firebase Console's Firestore Rules tab — without it every player's save would be world-readable/writable). `CloudSync.isConfigured()` gates the UI (disabled Sign In button + explanatory copy) for a fresh clone/fork that hasn't set up its own Firebase project yet.

**Gotcha**: `signInWithPopup` opening a blank/white popup that closes itself within about a second, with no error shown on-page, is `auth/unauthorized-domain` — Firebase auto-authorizes `localhost` and the project's own `*.firebaseapp.com` domain, but NOT a custom deployed domain. Fix: Firebase Console → Authentication → "Settings" tab (not "Sign-in method") → "Authorized domains" → Add domain → the real deployed hostname (e.g. `gayz.vercel.app`). Needed once per hostname the app is ever served from (would need re-adding if the domain ever changes).

## Standing rules for this project

- Every completed update gets committed, pushed to GitHub (`mrgulper/gayz`, private), and deployed to Vercel production (`npx vercel --prod --yes` → `gayz.vercel.app`) without asking each time.
- For batched/greenlit feature work, build straight through without stopping for confirmation checkpoints between items.
- Don't ship inert UI. If a feature's markup/CSS is scaffolded before its logic is wired up, leave it uncommitted rather than deploying a checkbox or HUD element that does nothing.

## Recurring bug classes

- **Shared-material mutation**: runtime flash/recolor effects (barrels, targets, hit-flash, etc.) must `.clone()` their material per instance. A shared module-level material fought over by simultaneous instances is a recurring source of visual bugs in this codebase.
- **Rotated-mesh AABB inflation**: `THREE.Box3.setFromObject()` on a rotated mesh inflates well past its visual footprint. Build axis-aligned collider boxes explicitly from known dimensions instead, for anything not axis-aligned.
- **`buildingLayout()` in `src/game/World.js` is fully deterministic** (seeded arithmetic, no `Math.random()`). Any "player stuck here" report can be root-caused by hand-computing the relevant building index's bounds directly from the array, rather than guessing from the visuals.
- **Safe zone (`buildSafeZone`) and street-grid buildings (`buildingLayout`) have no mutual awareness of each other.** They were placed independently. Before adding new safe-zone-interior features, check nearby `buildingLayout()` indices aren't secretly overlapping — building index 7 did (see `EXCLUDED_BUILDING_IDXS` in `World.js`) and silently bisected the compound with an invisible wall until root-caused.
- **The safe zone's position is `SAFE_ZONE_X`/`SAFE_ZONE_Z` (module-level constants in `World.js`, currently `0, 42` — moved once already from `-13, -10`).** Anything meant to live inside it should be positioned as an offset from these constants (like the Vault/practice range/trophy wall already are), never hardcoded absolute coordinates — `buildTraderStall`/`buildAmmoStation` used to hardcode their own position matching the *old* safe zone location, and got silently left behind on the last move until root-caused. Also re-check any other underground/surface structure whose fixed coordinates might now fall inside the safe zone's footprint (x=±7, z=±7 of center) — the sewer tunnel did.
- **Shared single-element toasts silently clobber each other.** `loreToast`/`companionBarkEl`/`achievementToast`/etc. are each one shared DOM element re-triggered via `classList.remove('show'); void el.offsetWidth; classList.add('show')` — if two calls to the same toast happen in the same synchronous tick (or before the CSS animation finishes), the first is silently skipped, never shown. Usually an accepted tradeoff for flavor/lore toasts, but worth a real queue (see `_achievementToastQueue`/`_drainAchievementToastQueue` in `Game.js`) for anything rare/precious enough that losing one matters — achievement unlocks got this fix after the completionist auto-cascade could unlock two achievements in one tick. Also check new fixed-position HUD elements (toasts, feeds, badges) against each other's screen coordinates — `#kill-feed` and `#achievement-toast` shipped at the same `top-right` slot until caught.
- **Every persisted stat is untrusted the instant Import Save exists.** `_importSaveFile` (Local Sharing batch) writes an uploaded file's contents into localStorage wholesale, so any field previously safe to interpolate raw into `innerHTML` because "it's always a number, this game itself only ever writes numbers here" no longer holds — a crafted save file can put a string there instead. `_safeStatNumber(v)` (coerces to a finite number, defined next to `_escapeHtml` in `Game.js`) and `_escapeHtml` are the two fixes; a security review caught 2 call sites on the Local Sharing batch's own new UI, and auditing the same pattern found 6 more in already-existing leaderboard/history renders (`_updateLeaderboardDisplay`, `_updateBossRushLeaderboardDisplay`, `_updateHouseholdLeaderboardDisplay`, `_updateHardcoreMemorialDisplay`, `_renderDailyLeaderboard`, the Run History list, the Profile stat grid) that had been safe until that same batch made them reachable from an untrusted file. Apply both defensively to any *new* code that renders a persisted field via `innerHTML` — treat "this value came from `this.xStats`/`this.xLeaderboard`/anything loaded via a `loadX()` function" as no safer than raw user input now, not just nickname-shaped fields.

## Gotchas

- `WeaponSystem.current` is a getter off `currentIndex` (`get current() { return this.weapons[this.currentIndex] }`). Assigning `weapons.current = X` is a silent no-op — set `currentIndex` instead.
- i18n keys (`src/game/i18n.js`) are only added to the English block in this codebase's current state — other language blocks are intentionally not kept in sync yet.
- Persistent (localStorage) vs per-run state: `MetaProgress.js`, `WeaponMastery.js`, `Achievements.js` persist across runs. `companionTrainingLevel`, `companionGear`, shop purchases reset on a fresh `new Game()` but survive a same-session "restart run" click — match this precedent for any new per-run state.

## Playwright verification quirks (no test suite exists — this is the actual verification method)

- Separate `page.evaluate()` calls can have multi-second real wall-clock gaps even for trivial scripts. Timing-sensitive assertions must happen inside one `evaluate()` call.
- `THREE` isn't globally exposed in the bundled build — `new THREE.Vector3()` inside `page.evaluate()` fails. Clone an existing Vector3 already in scope instead.
- Moving a mesh via `.position.set()` post-construction doesn't update `matrixWorld` until the next `renderer.render()`. Call `mesh.updateWorldMatrix(true, false)` before raycasting against a repositioned mesh.
- Fake zombie/rival test stubs need a `hittableMeshes: []` field or `WeaponSystem._fire()`'s `flatMap` throws.
- `Game.js`'s constructor sets `window.__game = this` at the very end, specifically so Playwright can drive real game methods without reaching into module scope — use `page.waitForFunction(() => window.__game)` to know the game finished constructing before calling anything on it.
- Headless Playwright can't actually grant real Pointer Lock (`THREE.PointerLockControls: Unable to use Pointer Lock API`) — the `lock`/`unlock` events this game relies on for pause-menu/audio state never fire from a real `.lock()` call in that environment. Set `game.gameStarted = true` (and whatever other flag the test needs) directly instead of assuming a `playBtn.click()` produced real lock state.
- Raycasting against a zombie (a `SkinnedMesh`) returns zero hits until `game.renderer.render(game.scene, game.camera)` has actually run at least once — `SkinnedMesh.raycast()` lazily computes its own world-space bounding sphere from live bone transforms, which are only ever baked by the renderer's normal per-frame `skeleton.update()`. Spawning a zombie and immediately calling `WeaponSystem._fire()`/a manual raycast in the same `evaluate()` silently misses every time; call `renderer.render(...)` once after positioning everything and before the raycast. Also don't aim at eye-height (~1.6) — this game's zombie mesh's own vertical extent is only about ±1 around its group origin, not a human eye-height collider.
- A synthetic event dispatched via `window.dispatchEvent(...)` never reaches a capture-phase listener registered on `document` (e.g. `PlayerController`'s mousemove interceptor) — `window` isn't in that event's propagation path unless the target is `document` itself or one of its descendants. Dispatch on `document` (or a real in-page element) instead of `window` when testing anything that relies on a `document`-level listener.
- `window.location.reload` can't be reliably stubbed from inside `page.evaluate()` (a plain `window.location.reload = fn` reassignment silently doesn't stick in Chromium) — and unlike an earlier note here, a real `location.reload()` firing *during* an in-flight `evaluate()` call (not just before/after one) reliably throws `Execution context was destroyed, most likely because of a navigation` and kills every other check queued in that same `evaluate()` call along with it. Test any reload-triggering action (Restore Defaults, Reset Progress, Hardcore respawn, Import Save, Clear Leaderboards) in its own isolated `page`/`evaluate()` call, wrapped in try/catch for that exact error, and verify the state it wrote (localStorage contents) via a follow-up read rather than trying to catch it mid-navigation. Don't issue your own `page.goto()` right after to force a clean reconnect either — it races the app's own in-flight reload and can lose with `net::ERR_ABORTED`; a plain `page.waitForTimeout(1500)` before the follow-up read is more robust than any explicit re-navigation.
- Two full `Game` instances (each its own WebGL context + running `requestAnimationFrame` render loop) constructing simultaneously in one headless browser is *slow* under load — measured over 20s just for the second one's constructor to finish, compared to ~1-3s for the first. If a test needs a second `page` (e.g. to verify state after a reload-triggering action from the point above), `await page.close()` the first one first rather than leaving it running in the background.
- `FileReader.readAsText(file)` on a `File` built from a `Blob` in a test never fired its `onload` callback at all in one observed headless Playwright run (silently hung forever, not slow) — even though the exact same code path worked correctly via manual testing expectations. `file.text()` (the modern Promise-based `Blob`/`File` method) doesn't have this problem and is simpler besides; prefer it over `FileReader` for anything reading an uploaded file, both in game code and in tests.
- The `#asset-loader` overlay (`src/main.js`, z-index 10, covers the whole page including `#menu`) doesn't hide on `window.__game` existing - it waits for 10 real `requestAnimationFrame` callbacks *after* construction (a deliberate GPU-warmup mask, see that file's own comment). In headless Playwright the FPS counter has been observed as low as ~1fps, so waiting that out for real can take many seconds and isn't worth it for a test that isn't specifically about the warmup itself - after `waitForFunction(() => window.__game)`, just force it directly: `page.evaluate(() => { const l = document.getElementById('asset-loader'); if (l) l.style.display = 'none' })`.
- `page.waitForFunction(() => window.__game, { timeout: 60000 })` has been observed reporting `Timeout 30000ms exceeded` - ignoring the explicit override - across multiple sessions now, cause still unconfirmed. A poll loop instead (`while` + `page.evaluate(() => !!window.__game)` + `page.waitForTimeout(500)`, throwing after your own deadline) sidesteps it entirely and has been reliable. Before blaming the app, also check for leftover Chromium processes from earlier crashed/never-closed test scripts (`ps aux | grep chromium`) - a build-up of dozens of them has caused a *new* page's Game construction to hang well past 60s in this same environment; `pkill -f chromium` between test batches (or whenever a run errors out before reaching `browser.close()`) keeps this from compounding.
- A macOS screenshot's filename (`Screenshot YYYY-MM-DD at H.MM.SS AM/PM.png`, saved to `~/Documents` or `~/Desktop`) uses a narrow no-break space (U+202F, not a regular space) between the time and AM/PM. A literal double-quoted path with a normal space silently fails with "No such file or directory" even though the file is right there in a directory listing - use a shell glob (`~/Documents/Screenshot*3.43.53*.png`) instead of typing the exact name. Separately, the Bash tool's default sandbox can't see files outside the project/scratchpad (e.g. `~/Documents`) at all - `dangerouslyDisableSandbox: true` is needed for a one-off `cp` to pull a user-provided image in, even once the filename issue above is fixed.

## Menu redesign notes (see `#menu` in `index.html`/`src/style.css`)

- `#menu-layout`/`#menu-hero`/`#menu-cards-row` all got explicit `z-index: 1` during the 3-column redesign, to sit above `#menu-bg`'s `z-index: 0` background layer - but every full-screen modal panel (`#upgrades-panel`, `#coinshop-panel`, `#credits-panel`, `#achievements-panel`, `#bestiary-panel`, `#profile-panel`, and the shared rule's other members) had no explicit `z-index` at all (auto), which loses to *any* positioned sibling with a real z-index regardless of DOM order. Net effect: the main menu rendered on top of every one of these "open" panels the whole time, so the nav buttons underneath stayed fully clickable through them - clicking a second nav button (e.g. Credits) while one panel was already open (e.g. Shop) opened the second on top without ever closing the first, producing a garbled double-panel mess. Fixed by giving the whole shared panel rule `z-index: 15` (matching `#settings-panel`, the one panel that already had this right). Any *new* full-screen overlay added to the menu needs to be checked against this same scale (`#menu-bg`=0, `#menu-layout`/`#menu-hero`/`#menu-cards-row`=1, `#play-btn.play-btn-centered`=5, `#asset-loader`=10, panels=15, `#ending-panel`/`#extraction-screen`=20, `#cinematic-bars`=25, `#screen-fade`=30) rather than assuming DOM order alone will decide stacking - it won't, the instant any sibling has a non-auto z-index.
- `_updateTexts()` (`Game.js`) sets `.textContent` directly on several menu buttons/elements for i18n. Any button that also holds a child `<svg>` icon needs its label set via `button.querySelector('span').textContent = ...` instead (or `setAttribute('aria-label', ...)` for an icon-only button like `settingsBtn`) - a plain `.textContent =` on the button replaces *every* child, icon included, and silently reduces it to plain text. This has now bitten twice - first on `upgradesBtn`/`achievementsBtn`/`bestiaryBtn`/`coinshopBtn`/`settingsBtn` when the icon redesign shipped, then again on the Companion Role/Loadout `.role-btn`/`.loadout-btn` grid (their icons were silently gone the whole time the mockup-matching pass was in progress, until caught). A one-time audit isn't enough - when touching `_updateTexts()`, grep the whole function for `.textContent =` and check every target against whether it has an `<svg>` child, rather than assuming past fixes covered every case. Note `.role-btn` is also reused by plain-text trader-screen buttons (`#trader-role-*`) with no `<span>` at all - guard with `const span = btn.querySelector('span'); if (span) ... else btn.textContent = ...` rather than assuming every match in a shared-class loop has the same shape.
- The hero background is `#menu-bg-photo` (`public/images/menu-bg-city.jpg`, a real photo), animated via CSS only - a slow Ken Burns zoom on the photo itself, a couple of flickering ember/light glows (`#menu-bg-embers`, irregular keyframe spacing so it reads as fire rather than a clean pulse), and a light diagonal rain-streak overlay (`#menu-bg-rain`) - all paused under `prefers-reduced-motion: reduce`. **A live-3D version of this (making `#menu` transparent so the already-rendering `#scene` canvas showed through, since `_tick()`'s `composer.render()` has no `gameStarted` guard) was tried and reverted** - the user wanted animation *on the photo*, not the actual gameplay world as the background. That attempt is worth remembering for one reason even though it's gone: revealing the live canvas surfaced a real pre-existing bug where a few HUD/toast elements (`#hotbar-power-score`, the auto-perf-mode toast, kill feed, achievement toast) had no `gameStarted` gating of their own and would render if anything ever made the menu's backdrop non-opaque again. Those gating fixes (`if (!this.gameStarted) return` in `_showLoreToast`/`_showAchievementToast`/`_pushKillFeed`, `#hotbar-power-score` defaulting to `display:none`) were kept even after the revert, since they're correct regardless of what's behind the menu.
- `#menu-cards-row` is a 3-column grid in its own full-width row below `#menu-layout`, same as the original design - a same-session attempt to move it into a 4th column beside `#menu-layout` (using the ~700px that sits idle either side of the centered 1180px layout on a wide screen) got reverted at the user's request. The homepage needing zero scroll turned out to be a hard, standing requirement (asked for twice), eventually solved properly rather than by repeatedly re-guessing fixed-px trims: `.menu-card-list` (the longest of the 3 is Game Modes at 8 rows) gets `max-height: 20vh; overflow-y: auto;` always, tightened to `8vh` only inside `@media (max-height: 820px)` - so on anything reasonably tall all 3 lists show in full with no internal scrollbar, and only on genuinely short windows does the longest list gain its own small internal scroll instead of pushing the whole page into needing one. **Don't make this cap unconditional/global** - an earlier version applied the same tight cap at every window height and visibly truncated all 3 lists behind a needless scrollbar even on spacious 1080p+ screens, with a large stretch of empty background left below. Combined with `#menu`'s own padding/gaps and several panels' padding trimmed a further ~15-20% (nickname inputs, stat rows, panel padding, `#menu-col-left`'s padding-top), this reaches 0px overflow at 1920x1080, 1600x900, 1440x900, *and* 1366x768 - re-measure `menu.scrollHeight - menu.clientHeight` at all of these (not just one) after any future size change, since a fix that only targets one height can silently regress another.
- Two separate, compounding bugs caused the hero column's own content (title/tagline/stats) to render visibly off-center from `#play-btn.play-btn-centered` even though both were "centered" in some sense: (1) `#menu-layout`'s 3 grid tracks (`250px`/`up-to-560px`/`230px`, ~1086px total with gaps) don't add up to its own `max-width:1180px` box, and a CSS grid left-aligns its tracks inside extra container space by default - the ~94px difference sat entirely on the right, shifting the visible columns (and hero column's own center) ~47px left of the box's true (correctly viewport-centered) middle. Fixed by adding `justify-content: center` to `#menu-layout`, and by making the left/right columns equal width (`250px`/`250px` - they'd drifted apart over several unrelated edits) so the hero column's own midpoint has no independent reason to differ from the box's midpoint either. (2) Separately, `#play-btn.play-btn-centered`'s original `top/left:50%; transform:translate(-50%,-50%)` measured with a **computed `transform` of `matrix(1,0,0,1,0,0)`** (i.e. never actually applied, cause not identified - not a transition-timing race, confirmed no duplicate/conflicting `#play-btn` rule, `element.matches()` confirmed the selector genuinely matched) - `left`/`top`/`position` from that same rule all took effect correctly, only `transform` silently didn't, leaving the button's top-left corner (not its center) pinned to viewport 50%/50%. Replaced with `position:fixed; inset:0; margin:auto; width/height:fit-content` - centers without needing `transform` or the element's own dimensions at all, and is arguably the more robust technique regardless of what caused the original bug. If a *centered* fixed-position element (via transform or otherwise) is ever added to this menu again, verify with `getBoundingClientRect()` that its rendered center actually lands on `window.innerWidth/2` - don't assume a standard centering pattern took effect just because it looks visually close.

- A 17-feature homepage batch ("add all to the homepage") added real UI to `menu-col-left`/`menu-col-right`/hero (Continue card, Recommended Difficulty hint, Loadout Presets row, Achievement Showcase row, Season Progress bar, Spotlight ticker) and blew the zero-scroll budget by ~90px at the 900px-tall heights and ~90px at 768px, even though 1920x1080 stayed at 0px overflow the whole time (it already had slack; 900px/768px never do). Lesson for next time: a batch that adds several small elements across *multiple* columns is deceptively expensive, because `#menu-layout`'s row height is the *tallest* column, not the sum - estimate cost per-column, not per-feature, before assuming small individual additions are safe.

Replaced with a `tag`/`color` pair per achievement (a short monogram like `FB`/`5N` + a hex accent color) rendered as a small colored-border swatch, consistent with the emblem picker's existing visual language. Check for a codebase-wide styling convention like this (a comment on a *similar* existing element, not just a grep for the literal thing you're adding) before introducing a new visual pattern.
- `tHtml(key, params)` (`i18n.js`) is the existing convention for i18n strings that need inline `<b>` emphasis when rendered via `innerHTML` - the source string uses `**bold**` markdown-style markers (converted to `<b>` internally), not literal `<b>` tags. Used for the new How to Play walkthrough steps; writing raw `<b>` tags directly into an i18n string and rendering with plain `t()` (which does *not* HTML-escape, so it would have silently "worked") would have broken from the established pattern for no reason.
