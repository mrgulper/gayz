# Skins, Design a Skin, Gallery

Split out of the old `ui-and-menu.md` on 2026-11-13 (word for word, oldest first). Add new notes at the end.

- **Inventory > Character is a Kirka-style skin grid driven by `INVENTORY_SKINS` (Game.js, 2026-09-30).** A new skin is one entry there (`id`, `name`/`nameKey`, `rarity` from `SKIN_RARITIES`, 64x64 Minecraft-format `dataUrl`, `count(game)` - 0 hides it); card pictures are flat front views drawn from the texture (`skinFrontIconURL`), the left preview is its own `MenuAvatar3D` (`_invSkinAvatar3D`). Clicking a card opens Equip/Market/Sell/Inspect (`#inv-skin-menu`, one element shared by Character and Weapons cards - `_openInventorySkinMenu` moves it next to the clicked card's grid and keeps it inside the card; `_invSkinMenuKind` is `'character'`/`'weapon'`). **Inspect** opens `#inspect-dialog` (Kirka-style: title, rarity pill, owned count, big 3D stage) driven by `InspectViewer.js` - drag turns it on both axes, wheel/pinch zooms, no idle spin (removed 2026-10-10); in the Old theme its box is the torn panel paper with dark ink (`html.ui-theme-old #inspect-box`); it gets a fresh canvas every opening and disposes its renderer (`forceContextLoss`) on close, so it never holds a WebGL context while hidden. A weapon is shown via `_weaponDisplayClone` (shares the game's geometry/materials - never dispose them); a character is a fresh `buildTexturedCharacter` that `_closeInspectDialog` disposes. **The Market is player-to-player (since 2026-10-01 - the game itself sells no skins there).** Inventory's card menu is Equip / Market / Sell / Inspect like Kirka: **Market** opens the trade dialog's price picker (`#trade-dialog`, `_openTradeDialog('list')`, 5% fee shown, `_marketFee`) and writes a `marketListings` Firestore doc (`CloudSync.createMarketListing`) after taking the skin out of the seller's own save; **Sell** sells to the game for the fixed `sell` price (half `MARKET_PRICES[rarity]`; GaygarX 250 gems - half its 500 Shop price, so buy-then-sell never makes Gems). The Market panel (`#market-panel`, opened by `#market-btn`, which always sits right after Store: `_applyNavOrder` and index.html's anti-flash script give the 8 reorderable buttons even `order`s and Market `coinshop*2+1`; `#build-mode-btn` is `order: 99`) shows active listings (`fetchActiveMarketListings` - no orderBy, sorted client-side, since orderBy + the status filter would need a composite index) with a search bar and Items/Rarity dropdowns (`_renderMarketFilters`; a skin's `kind` defaults to `'character'`, a future weapon skin sets `kind: '<weaponId>'`). Buying is a transaction that flips the listing to `sold` (`buyMarketListing`, so two buyers can't both get it); your own listing opens "Take Back" (`cancelMarketListing`). Sellers are paid when they next open Inventory or the Market (`_claimMarketSales` -> `fetchUnclaimedMarketSales` + `claimMarketSale`, a transaction on `claimed`, so a sale pays once even with two devices). Signed-in Cloud Save account required to list/buy (`_marketUid`). Coins/skins stay client-trusted like everything else here; the `marketListings` rules in `FIRESTORE_SECURITY_RULES` only enforce shape and who may flip which status. Test seam: `game.__marketBackendForTests` (same 6 functions, in memory) - and in Playwright pin `_cloudUid` with a getter, since the real auth restore resets it to null a moment after boot. Market skins (`MarketSkins.js`) are still real `INVENTORY_SKINS` entries players can own and trade; there's currently no in-game source of new copies. Ownership is `shopProgress.charSkins` (`{id: count}`, numbers so Cloud Save's additive merge adds up trades across devices); selling/listing the equipped skin re-equips Default. Equipping (`_equipInventorySkin`) works for any owned entry with no per-skin code. Inventory > Weapons is the same card grid, one Default card per weapon (`_renderInventoryWeapons`); pictures are rendered once from each weapon's viewmodel by `_weaponThumbnails()` on a throwaway WebGLRenderer (own canvas, disposed + `forceContextLoss` after), with a RoomEnvironment - most gun materials are metalness 1 and render pure black without an environment. Hands are left out via `userData.isHand` (set in `Viewmodels.js`'s `buildHand`).

- **The Skin Designer lives in this repo now (`public/skin-designer/index.html`, 2026-09-30)**, served from the game's own origin and embedded in `#skindesigner-frame` (`SKIN_DESIGNER_URL`; `SKIN_DESIGNER_ORIGIN` is `window.location.origin`) - it used to be the separate gayzcharacterskindesigner.vercel.app project/repo, which is no longer needed. Its localStorage keys use a `skindesigner-` prefix on purpose: every `gayz-*` key on this origin is Cloud Save data (`isSyncedKey`), and saved skin slots are PNG data URLs far too large to sync. Keep any new designer key off the `gayz-` prefix. GayZ Features was ported earlier the same way (straight into `index.html`), so gayz-features.vercel.app isn't needed either.

- **HD skins - 2x/4x pixels (2026-10-11, Gaymi: "add more pixels, 2x or 4x or even more").** A skin may be 64, 128 or 256 pixels wide: the same Minecraft layout with every pixel split 2x2 or 4x4. The game's `loadSkinTexture` returns `width`/`height` in 64-layout units plus `scale` (UVs stay in those units, only the canvas keeps the real pixels), so `buildTexturedCharacter` needs nothing else; anything cropping a skin picture by hand multiplies by `scale` (`_updateMenuAvatarPhoto`, `skinFrontIconURL`); Upload accepts the three sizes. In Design a Skin (`public/skin-designer/index.html`) the atlas is `SIZE` = 64 x `RES` (`setRes`, the Pixels 1x/2x/4x buttons, saved in `skindesigner-res-v1`, default 2x): editor code works in atlas pixels (`SIZE`, `pixelFaceRects`, `pz()` in the 2D view), the generator still paints in 64 units on `genCanvas` (`atlasCtx` is swapped to it for each stage) and `hdDetail` scales it up with Scale2x/EPX restricted to each face (crisp, never blurred - a first blended version came out soft), then adds hair strands and light. Loaded images never lose pixels (`drawImageToAtlas` picks the larger of the setting and the image), undo entries carry their own size. Game.js accepts designer skins up to 1.5 MB of data URL. **8x and 16x (512/1024 wide) were added the same day** (`RES_LEVELS`): the generator just runs Scale2x more times; the 3D preview's grid texture grows with the atlas (`gridScale()`), the 2D view goes down to 1 screen pixel per atlas pixel, undo keeps fewer steps (8 at 16x - 4 MB each), the palette samples every 2nd/4th pixel, Download Big is twice the skin's size. Generated 16x skins are only ~170 KB as PNG, so they sync and save like any other; servers get a 4x/2x/1x copy under `SERVER_SKIN_MAX` (`serverSkin()` in ServerBrowser.js) instead of the default skin. Test: "Design a Skin works at 8x and 16x" / "the game wears a 16x skin" in `tests/skindesigner.spec.js`. **Pixels changes really change the skin (2026-10-11, "I see no difference"):** the Pixels buttons redraw an unedited generated skin at the new size from the same plan (`lastGen` + `atlasSignature()`, `generateThemedSkin(..., fast)`), and Scale2x-upscale anything else; `hdDetail` adds face-edge shadow, top-edge light, hair strands + shine, cloth weave (not on the base head), skin grain and eye catchlights, scaled by `RES`; `scale2x` keeps the face below the hairline square (`crisp`) and only rounds strong edges (soft shading steps rounded into blobs and slanted mouths). Randomize's note comes from `describePlan(lastPlan)`. "No"/"without" words: `parsePrompt` fills `without` (`NEGATORS`/`NEGATABLE`; negators survive `understandWord`), and every `gear*` painter is wrapped by `skippable()`/`leftOut()` so a look's own gear is left off too. Inspect (`InspectViewer` `MIN_ZOOM`/`MAX_ZOOM`) and the designer's OrbitControls zoom have practically no limit.

- **Gallery (2026-10-16, Gaymi: "move the gallary to beside design a skin ... 3 sections for Character Weapon and Map ... where everyone can see, like, and comment").** The Gallery is a footer link (`#nav-gallery-link`, after Design a Skin), no longer a nav button. `GalleryUI.js` (plain functions taking `game`, state on game: `_galleryKind`, `_galleryPosts`, `_galleryOpen`, `_galleryDraft`, `_galleryLiked`) has four views inside `#gallery-content` (list / weapon Coming Soon / post form / detail). Firestore: one `gallery/{postId}` collection with a `kind` field ('character' or 'map'; no weapon posts yet), `likes/{uid}` (likes may only go +1 in the batch that creates the like doc, like `sharedMaps`) and `comments/{commentId}` (deletable by the commenter or the post's creator) - all in `FIRESTORE_SECURITY_RULES`, so **the owner must re-paste the whole ruleset** for it to work. Listing is `where kind ==` with no orderBy (sorted client-side - no composite index). Design a Skin's Post to Gallery posts `{type: 'gayz-gallery-skin', dataUrl, name}` to the parent (same origin/source check as Send to GayZ) and opens the post form; HD skins are posted as the biggest 4x/2x/1x copy under `SKIN_POST_MAX`. The Map Editor's Post to Gallery (`BuildShare.postToGallery`) shares the map under a code first and posts a 320x180 picture with `mapCode`, so Gallery's Play/Edit buttons open it through `share.openCode`. Every untrusted field is escaped; pictures must be png/jpeg data URLs. Test seam: `game.__galleryBackendForTests` (tests/gallery.spec.js). Clan invites take a name or #ID (`_sendClanInviteClick`, suggestions from the shared `_searchPlayerNames`, `#clan-invite-suggestions`). `.nickname-input`/`.search-bar` are softer since the same day (faint see-through fill + gentle rim in Golden, parchment + brown rim in Old, end of style.css) and Design a Skin's buttons/inputs/swatches are all ovals.

- **Design a Skin reads everyday words (2026-10-11, Gaymi: "make it think like a very smart AI because some common words it might not even know").** Still fully offline - no AI service, no API key, no cost. In `public/skin-designer/index.html`, `parsePrompt` first runs every word through `understandWords()`: a known word stays; `WORD_MEANINGS` turns everyday words into what the generator draws ("cowgirl" -> `cowboy girl`, "sexy"/"fancy" -> `stylish`, "goggles" -> `glasses`, "santa" -> `casual red white beard beanie`); word endings are tried (plurals, -ed/-ing/-y...); and a near miss becomes the closest known word (`editDistance`, 1 letter, 2 for words of 7+; `PLAIN_WORDS` are never "corrected"), listed in the result as `Read "pirte" as pirate`. 18 looks were added to `THEMES` (stylish, cowboy, chef, firefighter, farmer, scientist, gamer, athlete, suit, prisoner, sailor, miner, clown, superhero, ghost, alien, skeleton, mummy - each with `THEME_GEAR` from the existing gear painters; the last four are in `NON_HUMAN_THEMES`) plus ~40 `COLOR_WORDS`. Rules that bite: never put a part word (`hair`, `skin`) in `PLAIN_WORDS` - colour/style words read the word after them ("red hair"), and never let a meaning put a colour word right before a person word ("goth" -> `shadow black` made "goth girl" a black skin tone via `SKIN_WORDS`). A new word goes in `WORD_MEANINGS` (or the matching table); test: `tests/skindesigner.spec.js` (it serves three.js from `node_modules`, since the designer's import map points at a CDN).

- **2026-10-12 round 2.** Smart Edit: an asked hat colour is `parsed.overrides.hat` -> `p.hat`, read by every hat-drawing call (`applyGearWord` and all 18 headwear calls in `THEME_GEAR`); hats used to take `shade(p.shirt, -15)` (a white shirt gave a white hat). GayZ Features: only `#features-layout` scrolls (`#features-content` is a fixed flex column) so jumping to a section never moves the search bar. Map Editor entry fades too (`_fadeScreen(1, EDITOR_FADE_OUT_MS)`); the fade back in is `FADE_IN_SLOW_MS` when the load took over `FADE_LAG_LOAD_MS` or one of the first 4 frames took over `FADE_LAG_FRAME_MS`, else `FADE_IN_FAST_MS` (`_lastFadeIn` records why). Zombie corpses (`BuildSurvival._spawnCorpse`/`_updateCorpses`): a clone of the dead zombie's body with its **own material copies** (never the batch's shared ones), tipped away from the shot around its feet (`CORPSE_FALL`), arms lowered, lies `CORPSE_LIE`, fades `CORPSE_FADE`, max `MAX_CORPSES`; mirrored clients spawn one when the host stops listing a zombie. Windows: `CRACK_LOOKS` seeded crack pictures (one InstancedMesh per look in `_crackMeshes`) and `BREAK_LOOKS` shatter styles with 4 shard shapes (`_shardShapes`). Weapon models can leave out small loose pieces (`drop` in `WEAPON_MODELS`, `dropPieces` in Viewmodels.js - matched by the piece's middle in the model's own coordinates, at most `DROP_MAX_TRIANGLES`); the flamethrower's top sight is dropped (it blocked the crosshair when aiming). `WEAPON_THUMBS_CACHE` is v2 for it.

- **Design a Skin: slim arms, buttons under the character, many more words, Reset to my skin (2026-10-17, Gaymi: "make the 3px how minecraftskins.com does it ... move it under the characters ... any word thats an offical word will work").** Under the 3D preview (`.stage-actions`): `#armClassicBtn`/`#armSlimBtn`, then `#downloadBtn` / `#importBtn` ("Upload from Computer", the old toolbar Import button moved here, same ids) / `#resetBtn`. **Slim arms** are 3 wide: the PNG itself says which (each arm's last 2 side columns, x 54-55 / 46-47, rows 20-31 / 52-63, are empty on a slim skin) - `detectSlim()` in the designer and `_isSlimSkin()` in `MenuAvatar3D.loadSkinTexture` (returns `slim`; `buildTexturedCharacter` makes 3-wide arms at x=+-5.5) use the same test, so nothing extra is saved or synced and servers/other players get it for free. In the designer `BOXES`' arm entries are switched in place (`setArmDims`), the arm meshes rebuilt (`rebuildArmMeshes`), and the switch moves the painted pixels over (`convertArms`: 4->3 drops each narrowed face's 2nd column, 3->4 doubles it); loading any image (`drawImageToAtlas`) detects the shape, a blank one keeps the pick (`skindesigner-arms-v1`). The generator always paints classic and converts each stage when slim. Undo entries carry `.slim` (`snapshot()`/`restoreSnapshot()`). **Reset to my skin** reads `window.parent.__game.settings.customSkinDataUrl` (same origin), else the default skin - it used to load an unrelated bundled sample skin (the grey "G" one). **Words:** `MORE_MEANINGS` (an array of [meaning, words] - an object would drop repeated meaning keys) adds ~1,600 words to `WORD_MEANINGS`; every meaning may only use words the parser knows (test "Design a Skin knows many more words" checks it via `window.__moreMeanings`). `understandWord` also splits two words run together ("zombiecat"); everyday words that describe nothing are added to `PLAIN_WORDS` (filtered against known words); a several-word meaning containing a skin-tone word is followed by `MEANING_END` so "herobrine boy" can't make a white skin tone; a prompt with nothing recognised gets `parsed.guessed` (theme + colour from `hashString` of the words - same words, same look) instead of a random skin. Smart Edit reads "left/right arm/leg/hand/foot/sleeve" as one part (`LIMB_PARTS`, both layers, `recolorWhole`).

## Design a Skin: smarter Generate and Smart Edit (2026-10-18)

Gaymi: "make the edit and generating a skin smarter" - chose to stay offline (no AI service, no cost), with chat-style editing, 4 options and click-a-part. All in `public/skin-designer/index.html`; tests at the end of `tests/skindesigner.spec.js`.
- **Sentences:** `linkDescriptions()` runs on the raw words before `understandWords` (which drops "is"/"and"): part + `LINK_WORDS` + colour becomes colour + part ("hair that is red" -> "red hair"); `:`/`=` read as "is"; "red and black shirt" -> "red shirt black trim" (one word may sit between). `DESCRIBED_GEAR` (hat, cap, helmet...) takes a colour as `colors.hat` -> `p.hat`. In `parseEdit`, a colour word already used as a colour is no longer also a theme ("make this gold" used to re-theme the whole skin).
- **Generated-skin memory:** `rememberGen()` stores every generated skin's recipe (parsed, variant, seed, plan) keyed by `atlasSignature()`; `currentGen()` finds it again, so Smart Edit keeps the "redraw the same plan" path after Undo/Redo or picking an option. Never set `lastGen` with a sig by hand - go through `rememberGen`.
- **4 options:** `makeOptions()` (inside `runGeneration`, while `generating` is true) draws 3 more from other variants (other themes too when the prompt had none, or Randomize), snapshots each, puts the first back. `#genOptions` shows flat front views (`optionThumb`). Hidden on slot switch and Pixels change (stale size). ~4 s at 16x.
- **Chat:** `editChat` (lastPart, last {actions, part, sig}, turns). `parseEdit(text, startPart)` uses the remembered part for a colour with no part. `UNDO_ASK`/`REDO_ASK`/`AGAIN_ASK` (repeats shade/tint only); `CORRECTION` ("no, blue", "nope", "actually ...") undoes the last change only if the picture still matches `editChat.last.sig`. "no hat" stays a removal ("no" needs punctuation, or nothing else readable). New action `tint` ("more blue", "bluer", `mixHex`). "match the pants" alone uses the last part; "remove it" after an add removes what was added. `#aiEditNote` is now a div holding the last 4 turns + follow-up buttons (`data-ask`).
- **Pick a part:** `#aiPickBtn` arms `pickArmed`; the 3D pointerup calls `pickAt(hits)` (first hit with an opaque pixel). `pickState` = one box's one layer, pixels within 80 of the tapped colour (`mask`), plus the mirror limb (`mirror`, for "both"). Part words go to `'picked'` (`PART_LABELS.picked` = `pickLabel`). `editPicked` recolours the mask keeping shading; remove only on the outer layer. `flashPixels` lightens the patch for 420 ms; `cancelFlash()` runs from `pushUndo` and the save timer so the flash never gets saved. Pick clears on slim/classic switch, Pixels change, new skin, upload, slot switch. Test hook `window.__pickAt(px, py)`.
