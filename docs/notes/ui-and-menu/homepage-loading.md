# Homepage loading, first paint, lag

Split out of the old `ui-and-menu.md` on 2026-11-13 (word for word, oldest first). Add new notes at the end.

- **The full-screen "GayZ ran into a problem loading" message (inline safety-net script at the end of `index.html`) only listens while loading** - its `error`/`unhandledrejection` handlers return once `window.__game` exists (2026-10-03). Before that, any stray mid-game error (a sound that couldn't play, a dropped request) covered a game that was still running fine. Real load failures still show it.

- **Lighter homepage on touch devices (2026-10-12, iPad: "lagging crazy" on opening, gameplay fine).** `src/game/LiteHome.js` (`LITE_HOME` = `(hover: none) and (pointer: coarse)`, also `html.lite-home` from index.html's first script): rain/water canvases at pixel ratio 1, water redrawn at most every 33ms with 3px rows, 60% of the drops, the menu avatar at pixel ratio 1.25 and 30 fps unless dragged, `#menu-bg-fog`/`#menu-bg-ash` animations off, and rain/water start only after `html.game-ready` (`startWhenLight`). Round 2 the same day ("still lagging crazy"): fog/ash are `display: none`, the photo's Ken Burns zoom is off, the water uses a normal blend instead of `screen` (a blended layer inside an animated one re-composited the whole screen every frame - the cost a headless profile can't see), and rain/water/avatar all draw at `LITE_FRAME_MS` (30). **The game clock must tick in the map:** `_tick`'s Build Mode branch calls `this.timer.update()` before `getDelta()` - it used to only be updated on the homepage, so every game frame reused the last homepage frame's step (THREE.Timer keeps `_delta` in ms) and a laggy phone homepage made the game run 2-3x too fast (test: "the game clock keeps ticking in the map"). Measured at iPad size with a 4x-slowed CPU: homepage 8 -> ~21 fps after load, 6 -> ~14 while loading; turning layers off one by one showed rain, water, avatar and the fog/ash group each costing about as much as the others. Computers are untouched. The landscape-tablet character (`#setup-avatar-wrap` in the 701-1300px landscape block) is also capped by `calc(100dvh - 340px)` (width = height x 0.48), so a two-line name plate (clan) plus the footer always fit - it used to be sized from the width alone and pushed the footer off an iPad's screen.

- **One homepage clock, and Design a Skin preloaded (2026-10-16, "the homepage lags on both mobile and keyboard devices ... design a skin takes pretty slow to load").** Measured with a Chrome trace (paint/raster/commit time, not just fps - headless fps mostly measures software compositing): the ash layer animated `background-position`, a full-screen repaint every frame (~1.4 s of raster work per second at 1600x900 x2), so it moves with a `transform` now (one tile taller than the screen); the water and ash dropped `mix-blend-mode: screen` and the fog its `blur()` on every device, not just touch. The rain, road water and spinning character no longer run three separate rAF loops: they all draw on `LiteHome.onHomeFrame`'s shared beat (60/s on computers, 30/s on touch), so the background stack is re-blended once per beat instead of whenever any one of them changed. A computer whose homepage averages slower than `SLOW_FRAME_MS` over `SLOW_SAMPLE` frames after `game-ready` gets `html.home-slow` (same still background as `html.lite-home`) and the 30/s beat - headless Chromium always lands there. Canvases draw at 1x (rain/water) and the character at 1.5x max; a `noSpin` preview (Inventory) redraws only every `STILL_REDRAW_MS` unless dragged. Design a Skin's iframe is pointed at the designer `SKIN_DESIGNER_PRELOAD_MS` after boot in idle time (`_preloadSkinDesigner`, waits while a game is running/starting); the designer's `animate()` draws nothing while its canvas has no size or the tab is hidden, so the hidden panel costs nothing (test: "Design a Skin is loaded ahead of time and idle while hidden"). Any new homepage animation goes on `onHomeFrame` and must not animate `background-position`, `filter` or a blended layer.

- **The homepage's first paint IS its final look - nothing may jump into place once the game has loaded (2026-10-09, root-cause fix; Gaymi: "when refreshing you still see the old thing, then when it's done it's gone").** `Game()` is only built after the whole bundle and the gun models load (seconds on a slow connection), so anything it measured or filled in used to appear late: the right column at full size then shrinking, the footer links centered then sliding, the profile card/currencies/clock missing, English labels then translated. Now: (1) the three layout fitters (right column zoom, Play centering, footer links) live in an inline script in `index.html` (`window.__menuLayout.fit()`), run right after the menu markup, on resize, on `fonts.ready` and on `load`; Game.js only calls `_fitMenuLayout()` when text changes - **never put homepage layout measuring back into Game.js only**; (2) `_saveMenuPaintCache()` (at game-ready, `pagehide`, tab hidden) stores the text + inline display of every leaf element under `MENU_PAINT_CACHE_ROOTS` (currencies, profile card, showcase header, hero, nav, footer links) in `localStorage['menu-paint-cache']` (device-only), and the inline script repaints them before first paint - per root, only if the leaf count still matches, so a changed page never gets text in the wrong spots; it adds `html.menu-cached`, which un-hides the save-driven values early; the clock is computed inline (`.early-painted`); (3) the theme's background photo is preloaded from the head's theme script. A new homepage element whose text or size comes from the game goes under one of those roots (or its own early inline code), and `tests/construction.spec.js` "paints its final layout before the game has loaded" holds the game's scripts back and compares the page with the loaded one.

- **Every homepage picture is part of the stylesheet (2026-10-09, reported three times the same day: "when refreshing it goes from the first image to the second ... fix it fully").** The background photo, logo, button plates, PLAY plate, settings gear, profile plate/coin/face-wear live in `src/menu-art/` (right-sized WebP, ~590 KB for both themes) and `vite.config.js`'s `build.assetsInlineLimit` inlines that folder into the CSS - the stylesheet must load before anything paints, and Chrome keeps the previous screen up during a reload until then, so a refresh goes straight from the old full page to the new full page. As separate files they arrived after the first paint (bare text, then pictures). **Rejected the same day, don't bring back:** a dark "wait until loaded" screen ("i dont like it") and tiny blurred stand-ins ("dont make the page blurry"). The logo is a `<span id="menu-title-img" role="img">` with a CSS background now, not an `<img>`. A new picture on the homepage's first screen goes in `src/menu-art/` and is referenced from style.css with a relative `./menu-art/...` path - keep it small, everything there loads with the stylesheet. `__menuLayout` re-fits on `#menu-hero` size changes (ResizeObserver, deferred one frame - doing it inside the observer raised a "ResizeObserver loop" error). **Gallery** has its own panel (`#gallery-panel`, `/gallery`, `_openGalleryPanel`; Coming Soon).

- **The "problem loading" safety net (end of index.html) waits before covering the page (2026-10-09, "i wasnt able to open gayz").** It used to show the instant any error/unhandled rejection happened before `window.__game` existed - even ones the game survives. Now an error starts an `ERROR_GRACE_MS` (8s) timer and the screen only shows if the game still isn't built by then (and is removed if it turns up later); it ignores the browser's "ResizeObserver loop" notice and prints the actual error message small at the bottom, so a player's screenshot says what broke.

- **Homepage first paint must match the loaded game (2026-09-30 report: "I see the Golden look first, then it switches").** The inline theme script at the top of `index.html` must use the same default as Game.js's settings loader (Old unless `uiTheme === 'golden'`) - it used to check for an explicit `'old'`, so new players and devices whose save hadn't arrived yet painted Golden first. `main.js` re-applies the theme class after the pre-boot cloud pull. Save-driven values (`#menu-currency-bar`, `#menu-player-badge`, `#homepage-clock`) stay `visibility: hidden` until Game.js adds `html.game-ready` at the end of its constructor, instead of showing 0s/`#PLAYER` placeholders. A new save-driven homepage element belongs on that list.
