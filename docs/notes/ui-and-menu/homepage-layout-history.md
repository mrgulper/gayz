# Homepage layout history (centering, z-index, redesigns)

Split out of the old `ui-and-menu.md` on 2026-11-13 (word for word, oldest first). Add new notes at the end.

- `#menu-layout`/`#menu-hero`/`#menu-cards-row` all got explicit `z-index: 1` during the 3-column redesign, to sit above `#menu-bg`'s `z-index: 0` background layer - but every full-screen modal panel (`#upgrades-panel`, `#coinshop-panel`, `#credits-panel`, `#achievements-panel`, `#bestiary-panel`, `#profile-panel`, and the shared rule's other members) had no explicit `z-index` at all (auto), which loses to *any* positioned sibling with a real z-index regardless of DOM order. Net effect: the main menu rendered on top of every one of these "open" panels the whole time, so the nav buttons underneath stayed fully clickable through them - clicking a second nav button (e.g. Credits) while one panel was already open (e.g. Shop) opened the second on top without ever closing the first, producing a garbled double-panel mess. Fixed by giving the whole shared panel rule `z-index: 15` (matching `#settings-panel`, the one panel that already had this right). Any *new* full-screen overlay added to the menu needs to be checked against this same scale (`#menu-bg`=0, `#menu-layout`/`#menu-hero`/`#menu-cards-row`=1, `#play-btn.play-btn-centered`=5, `#asset-loader`=10, panels=15, `#ending-panel`/`#extraction-screen`=20, `#cinematic-bars`=25, `#screen-fade`=30) rather than assuming DOM order alone will decide stacking - it won't, the instant any sibling has a non-auto z-index.

- The hero background is `#menu-bg-photo` (`public/images/menu-bg-city.jpg`, a real photo), animated via CSS only - a slow Ken Burns zoom on the photo itself, a couple of flickering ember/light glows (`#menu-bg-embers`, irregular keyframe spacing so it reads as fire rather than a clean pulse), and a light diagonal rain-streak overlay (`#menu-bg-rain`) - all paused under `prefers-reduced-motion: reduce`. **A live-3D version of this (making `#menu` transparent so the already-rendering `#scene` canvas showed through, since `_tick()`'s `composer.render()` has no `gameStarted` guard) was tried and reverted** - the user wanted animation *on the photo*, not the actual gameplay world as the background. That attempt is worth remembering for one reason even though it's gone: revealing the live canvas surfaced a real pre-existing bug where a few HUD/toast elements (`#hotbar-power-score`, the auto-perf-mode toast, kill feed, achievement toast) had no `gameStarted` gating of their own and would render if anything ever made the menu's backdrop non-opaque again. Those gating fixes (`if (!this.gameStarted) return` in `_showLoreToast`/`_showAchievementToast`/`_pushKillFeed`, `#hotbar-power-score` defaulting to `display:none`) were kept even after the revert, since they're correct regardless of what's behind the menu.

- `#menu-cards-row` is a 3-column grid in its own full-width row below `#menu-layout`, same as the original design - a same-session attempt to move it into a 4th column beside `#menu-layout` (using the ~700px that sits idle either side of the centered 1180px layout on a wide screen) got reverted at the user's request. The homepage needing zero scroll turned out to be a hard, standing requirement (asked for twice), eventually solved properly rather than by repeatedly re-guessing fixed-px trims: `.menu-card-list` (the longest of the 3 is Game Modes at 8 rows) gets `max-height: 20vh; overflow-y: auto;` always, tightened to `8vh` only inside `@media (max-height: 820px)` - so on anything reasonably tall all 3 lists show in full with no internal scrollbar, and only on genuinely short windows does the longest list gain its own small internal scroll instead of pushing the whole page into needing one. **Don't make this cap unconditional/global** - an earlier version applied the same tight cap at every window height and visibly truncated all 3 lists behind a needless scrollbar even on spacious 1080p+ screens, with a large stretch of empty background left below. Combined with `#menu`'s own padding/gaps and several panels' padding trimmed a further ~15-20% (nickname inputs, stat rows, panel padding, `#menu-col-left`'s padding-top), this reaches 0px overflow at 1920x1080, 1600x900, 1440x900, *and* 1366x768 - re-measure `menu.scrollHeight - menu.clientHeight` at all of these (not just one) after any future size change, since a fix that only targets one height can silently regress another.

- Two separate, compounding bugs caused the hero column's own content (title/tagline/stats) to render visibly off-center from `#play-btn.play-btn-centered` even though both were "centered" in some sense: (1) `#menu-layout`'s 3 grid tracks (`250px`/`up-to-560px`/`230px`, ~1086px total with gaps) don't add up to its own `max-width:1180px` box, and a CSS grid left-aligns its tracks inside extra container space by default - the ~94px difference sat entirely on the right, shifting the visible columns (and hero column's own center) ~47px left of the box's true (correctly viewport-centered) middle. Fixed by adding `justify-content: center` to `#menu-layout`, and by making the left/right columns equal width (`250px`/`250px` - they'd drifted apart over several unrelated edits) so the hero column's own midpoint has no independent reason to differ from the box's midpoint either. (2) Separately, `#play-btn.play-btn-centered`'s original `top/left:50%; transform:translate(-50%,-50%)` measured with a **computed `transform` of `matrix(1,0,0,1,0,0)`** (i.e. never actually applied, cause not identified - not a transition-timing race, confirmed no duplicate/conflicting `#play-btn` rule, `element.matches()` confirmed the selector genuinely matched) - `left`/`top`/`position` from that same rule all took effect correctly, only `transform` silently didn't, leaving the button's top-left corner (not its center) pinned to viewport 50%/50%. Replaced with `position:fixed; inset:0; margin:auto; width/height:fit-content` - centers without needing `transform` or the element's own dimensions at all, and is arguably the more robust technique regardless of what caused the original bug. If a *centered* fixed-position element (via transform or otherwise) is ever added to this menu again, verify with `getBoundingClientRect()` that its rendered center actually lands on `window.innerWidth/2` - don't assume a standard centering pattern took effect just because it looks visually close.

- An "AAA menu polish" pass (bigger title/logo, thicker/darker panel borders, glowing Play button, drifting ash/fog background layers, per-class/difficulty glow) pushed total menu height back over 1080px (a fresh regression each time - a bigger title, more `#menu-hero` gap, thicker panel padding, and even a `.mode-toggle` hover-padding tweak each add a few px that compound across many repeated elements, e.g. 2px of extra checkbox-row padding × 19 checkboxes = 38px). No single trim fixes this - it needs re-measuring `menu.scrollHeight - menu.clientHeight` at 1920x1080 after each visually-significant size increase and clawing the difference back from low-visual-cost spots (`#menu-col-left`'s old 34px `padding-top`, reserved for the FPS counter overlapping the menu, turned out to be unnecessary - the counter only reaches `opacity:1` in the same synchronous handler that sets `menu.style.display='none'`, so there's never a frame where both are visible). Also: `#round-mode-hint`/`#controls-list` were hidden (`display:none`) as part of this same pass to declutter the hero column - `_updatePlayBtnCentering()` used to measure clearance from `#controls-list`'s `getBoundingClientRect()`, which returns all-zero for a `display:none` element and would have silently broken the centering math; it now measures from `#settings-btn` instead (the new last-visible hero element). Any future hide of a hero-column element needs the same check.

- A "military stencil" reskin pass (matching a reference mockup) added: `#menu-title` uses the 'Black Ops One' Google Font (loaded alongside Bebas Neue in `index.html`'s `<head>`) instead of Bebas Neue, with layered dark/red text-shadow + two small blood-drip `::before`/`::after` accents - unlike Bebas Neue, Black Ops One has true (visually distinct) lowercase glyphs, so both `#menu-title` and `#play-btn` need an explicit `text-transform: uppercase` now or the source HTML's mixed-case text (`GayZ`, `t('playBtn')`) shows through literally instead of reading as full caps. Companion Role + Loadout got visually merged into one "Choose Class" 2x3 `.class-grid` (still two functionally-separate settings underneath - `data-role`/`.role-btn` for the companion, `data-loadout`/`.loadout-btn` for the player build - only the two `<h2>` sub-headings and the `#companion-role-row`/`#loadout-row` container split were removed), each class/difficulty getting its own accent color via `--menu-green`/`--menu-orange`/`--menu-blue`/`--menu-purple`/`--menu-red` attribute-selector rules (`.class-btn[data-role="melee"]` etc.) instead of every button sharing the one gold "active" treatment. Every `.menu-panel`/`.menu-card`/`#menu-nav-buttons button` got small gold corner-bracket `::before`/`::after` marks (top-left + bottom-right only, not all 4 - simpler than sourcing/building a full corner-bracket SVG per corner) instead of a plain rounded border, and `#play-btn` got an octagonal `clip-path` + 4 small rivet dots (layered `radial-gradient`s under the main gold fill) instead of a rounded pill.

- `#play-btn`'s dead-center positioning (`.play-btn-centered` class) is decided live by `centerPlayBtn` in index.html's inline `__menuLayout` (was `_updatePlayBtnCentering()` in Game.js until 2026-10-09), not a CSS media-query height breakpoint - an earlier `@media (min-height: 900px)` version shipped, then broke on a real screen because it didn't account for the news-ticker/weekly-mutator lines being variable-length i18n text that pushes everything below it further down than a quick empty-content test showed. Any time something's on-screen fit depends on the size of OTHER elements that aren't fixed at build time (dynamic text, i18n string length, rotating content), measure the actual gap live via `getBoundingClientRect()` (temporarily toggling `display:none` on the element being positioned to get an accurate "what if it wasn't here" measurement) rather than guessing a pixel breakpoint - re-run on `resize` too.

- "Make everything bigger" was said twice before landing right - the first pass only bumped font-sizes on nav buttons/checklist/labels, which the user explicitly called too narrow ("no just shop upgrade etc make everything in the homeepage bigger" - repeated verbatim). A genuine "everything bigger" scale-up means every dimension, not just text: `#menu-layout`/`#menu-cards-row` grid tracks and max-width grew (`250px`→`290px` columns, `1180px`→`1320px` max-width), plus every icon (`.class-icon`, `#menu-nav-buttons button svg`, `#settings-btn svg`, `#menu-avatar-icon`/its svg, `.mode-icon`, `.mode-toggle input`), the title (`100px`→`114px`) and Play button (padding + font-size), and panel/card/nav-button padding all grew together. The zero-scroll compensation for a change this size was a single knob, not many small trims: tightening the existing short-window gate from `@media (max-height: 820px) { .menu-card-list { max-height: 8vh } }` down to `6vh` was enough on its own to hold 0px overflow at all 4 tracked heights (1920x1080/1600x900/1440x900/1366x768) - re-verify at all 4 after any future size pass, same as every prior round in this section.
