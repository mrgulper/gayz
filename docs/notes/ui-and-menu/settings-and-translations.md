- `_updateTexts()` (`Game.js`) sets `.textContent` directly on several menu buttons/elements for i18n. Any button that also holds a child `<svg>` icon needs its label set via `button.querySelector('span').textContent = ...` instead (or `setAttribute('aria-label', ...)` for an icon-only button like `settingsBtn`) - a plain `.textContent =` on the button replaces *every* child, icon included, and silently reduces it to plain text. This has now bitten twice - first on `upgradesBtn`/`achievementsBtn`/`bestiaryBtn`/`coinshopBtn`/`settingsBtn` when the icon redesign shipped, then again on the Companion Role/Loadout `.role-btn`/`.loadout-btn` grid (their icons were silently gone the whole time the mockup-matching pass was in progress, until caught). A one-time audit isn't enough - when touching `_updateTexts()`, grep the whole function for `.textContent =` and check every target against whether it has an `<svg>` child, rather than assuming past fixes covered every case. Note `.role-btn` is also reused by plain-text trader-screen buttons (`#trader-role-*`) with no `<span>` at all - guard with `const span = btn.querySelector('span'); if (span) ... else btn.textContent = ...` rather than assuming every match in a shared-class loop has the same shape.

- `tHtml(key, params)` (`i18n.js`) is the existing convention for i18n strings that need inline `<b>` emphasis when rendered via `innerHTML` - the source string uses `**bold**` markdown-style markers (converted to `<b>` internally), not literal `<b>` tags. Used for the new How to Play walkthrough steps; writing raw `<b>` tags directly into an i18n string and rendering with plain `t()` (which does *not* HTML-escape, so it would have silently "worked") would have broken from the established pattern for no reason.
