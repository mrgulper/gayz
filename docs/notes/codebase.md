# Codebase, tests and big plans

Moved out of CLAUDE.md on 2026-10-16 (word for word) so it is only read when needed. Newest notes for a topic go at the end of its file.

Browser Three.js zombie-survival FPS. Vite build, no framework. Verification is done by driving the real running game (Playwright, real game methods via `page.evaluate()`, not simulated input events) — both as a small committed suite and as one-off scripts.

**Tests + CI**: `tests/*.spec.js` is a committed Playwright suite (`npm test`, config in `playwright.config.js` - builds and runs against `vite preview` on port 4173, one worker, 120s per-test timeout, since each test constructs a real `Game()`). `.github/workflows/ci.yml` runs `npm run lint` → `npm run build` → `npm test` on every push/PR to `main`. The suite is narrow (build mode, construction, progression, save, settings) - it catches "the game no longer boots/saves", not feature-level regressions, so feature work still needs its own targeted Playwright check. Run it locally with `CI=1 npx playwright test` (without `CI`, `reuseExistingServer` will silently test whatever stale preview server is already on 4173). `tests/helpers.js`'s `hideAssetLoader` is a harmless no-op now (`#asset-loader` is gone, see Gotchas).

**`Game.js` split (in progress)**: `Game.js` is ~5.7k lines (12.3k before the 2026-10-16 split, ~26.6k before the old Map 1 was deleted); self-contained UI systems are being moved out into their own modules one slice at a time. Convention (same as `CloudSaveUI.js`/`MenuPresets.js`/`MenuEasterEggs.js`): plain exported functions taking `game` as an explicit first parameter (not a class, not a prototype mixin), called as `Module.fn(this, ...)` from `Game.js`; all state stays on the `Game` instance (`game._chatChannel` etc.), so nothing else that reads it has to change. Helpers the module needs from `Game.js` (`_escapeHtml`, `_censorText`, `saveSettings`, ...) are `export`ed from `Game.js` and imported back - the circular import is fine because they're only called at run time, never at module-evaluation time. Done so far: `CloudSaveUI.js` (Cloud Save panel), `ChatUI.js` (both chat surfaces + emoji picker + mute list), `GalleryUI.js`, and on 2026-10-16 with `scripts/move-to-module.py` (pure moves, one-line stand-ins left in Game.js): `SettingsUI.js` (every Settings tab, nav order, keybinds, save/settings codes), `FriendsUI.js` (Friend List, requests, other players' profiles), `OnlineUI.js` (leaderboards, poll, online stats, Google sign-in/restore), `ClanUI.js`, `InventoryUI.js` (Inventory, Store, Market, trade dialog, crates, weapon pictures), `ProfileUI.js` (Profile, auth card, skin upload, Levels), `ProgressUI.js` (run results, achievements, quests, Upgrades/Prestige, login streak, best stats), `InfoPagesUI.js` (GayZ Features, Patch Notes/What's New, update card, How to Play, Credits, Terms, Privacy). Game.js went from 12.3k to 5.7k lines. Good next candidates: the Online Features cascade (`_renderCloudOnlineSection` and everything it calls), the spotlight ticker, the Clan section (`_bindClanSection`), Settings panel binders. Do each slice as a pure move (mechanical `this.`→`game.` rewrite, no behavior changes mixed in), check every caller with a grep across `src/` (not just `Game.js` - `CloudSaveUI.js` calls into chat, `style.css` comments reference method names), and verify with lint + build + `npm test` + a targeted Playwright check of the moved feature.

**`3D_ASSET_OVERHAUL.md` (repo root)** holds a complete, adversarially-verified research handoff + phased plan for replacing all ~75 procedural models with real 3D assets at zero cost (CC0 packs / free tiers / Blender scripting). Self-contained — read it before starting any asset/visual-overhaul work.

**`docs/PERFORMANCE.md`** holds the measured diagnosis of the FPS bottleneck that `QualitySettings.js` was written around while it was "still unresolved" — it is resolved: the game is CPU-bound on scene-graph traversal (14,792 objects, 470 draw calls for 35k triangles), not GPU-bound, which is why lowering resolution and quality settings never helped. Self-contained, includes a reproducible measurement script and a full A/B/C implementation plan. **Read it before touching anything performance-related, and before flipping `LOW_QUALITY_MODE`.**
