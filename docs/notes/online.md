# Cloud Save, Firestore, online features and chat

Moved out of CLAUDE.md on 2026-10-16 (word for word) so it is only read when needed. Newest notes for a topic go at the end of its file.

**Cloud Save (`src/game/CloudSync.js`)**: Firebase Authentication (Google Sign-In) + Firestore — still no custom backend of our own, just Firebase's hosted services, and the `firebase` npm package is a real (non-dev) dependency now that it ships in the bundle. **Not** the original design: a first pass used raw Google Identity Services + Drive's `appDataFolder`, but that meant sending the project owner through Google Cloud Console's separate "Try Google Cloud for free" onboarding wizard (`console.cloud.google.com/freetrial/...`) to even reach the OAuth/API screens — a `$300 in free credit, 90 days` promo (not an actual charge, but confusing, and Step 2 of that wizard pushes phone/card verification) gated behind a product we didn't actually need. Firebase Console (`console.firebase.google.com`) reaches the same OAuth-client-creation + API-enablement outcome without that wall — its free "Spark" plan needs no billing account at all, and enabling the Google sign-in provider in Firebase Authentication auto-configures the underlying OAuth client for you (no manual consent-screen wizard). Lesson: when a Google Cloud Console flow demands billing/trial signup for something that should be free, check whether Firebase reaches the same product (Auth, Firestore, Functions are all still "Google Cloud" underneath) through its own console first, rather than pushing through the trial wall. The save blob synced to Firestore is the exact same `{localStorageKey: stringValue}` shape `_exportSave()`/`_importSaveFile()` already used for manual file-based sharing (`_snapshotLocalSave()`/`_applyImportedSaveData()` in `Game.js` are the shared helpers both paths call) — same untrusted-data handling applies (see the XSS note below), same reasoning: don't invent a second save format. `FIREBASE_CONFIG` in `CloudSync.js` holds the real `gayz-aa69c` project's config (not a secret — Firebase's web config only says which project to talk to; real security is `FIRESTORE_SECURITY_RULES`, exported from that same file, pasted into Firebase Console's Firestore Rules tab — without it every player's save would be world-readable/writable). `CloudSync.isConfigured()` gates the UI (disabled Sign In button + explanatory copy) for a fresh clone/fork that hasn't set up its own Firebase project yet.

**Gotcha**: `signInWithPopup` opening a blank/white popup that closes itself within about a second, with no error shown on-page, is `auth/unauthorized-domain` — Firebase auto-authorizes `localhost` and the project's own `*.firebaseapp.com` domain, but NOT a custom deployed domain. Fix: Firebase Console → Authentication → "Settings" tab (not "Sign-in method") → "Authorized domains" → Add domain → the real deployed hostname (e.g. `gayz.vercel.app`). Needed once per hostname the app is ever served from (would need re-adding if the domain ever changes).

**Online Features (leaderboard/weekly ranking/friend compare/global kill counter/community poll)**: layered on top of Cloud Save once Firestore already existed — same "extend the existing backend, don't invent a new one" reasoning as everything else in this section. Four new collections beyond `saves/{uid}`, all added to `FIRESTORE_SECURITY_RULES` in `CloudSync.js` (this is the FULL ruleset now, not additive — re-publishing it replaces whatever's currently live in Firebase Console, so always paste the whole exported string, never just a diff): `leaderboard/{uid}` (public read, own-uid write with type/range bounds - also doubles as the friend-compare lookup by nickname, no separate friends system needed), `weeklyLeaderboard/{week}/entries/{uid}` (same shape, fresh sub-collection per week so old weeks' rankings survive), `stats/global` (single doc, public read, signed-in-only `increment`-only write capped per call - **must be created once by hand** via Firestore Console's "Start collection" UI with a `totalKills` field set to `0`, since the rules deliberately block client-side `create` on it), and `polls/{pollId}/votes/{uid}` (one vote doc per account, `allow create` with no `update`/`delete` is what actually enforces one-vote-per-account - results read via a `getCountFromServer` aggregation query per option, never by downloading every vote doc). The one hardcoded poll (`POLL_ID`/`POLL_OPTIONS` in `Game.js`) is developer-authored content, not user-generated, so there's no moderation surface beyond picking a new `POLL_ID` for the next one (a new ID starts vote counts fresh rather than resetting the old poll's tally).

A follow-up round added: a **Global Rank badge** (`CloudSync.fetchMyGlobalRank` - a `getCountFromServer` count of leaderboard docs with a strictly better `bestNight`, +1 - appended to `#menu-player-tag` via the new `_renderPlayerTag()`, which replaced two duplicate inline call sites), a **nearest-rival nudge** (`fetchNearestRivalAbove` - same field, opposite direction, `limit(1)`), a **saved friends list** (`settings.savedFriends`, capped at 5, reuses the same leaderboard-by-name lookup the Friend Compare box already had), a **weekly-reset countdown** folded into the existing spotlight ticker's weekly-challenge mode (`_daysUntilWeekReset()` - deliberately doesn't re-derive the ISO-week math by hand; it feeds future dates back through `_thisWeekStr()` itself so it can never drift out of sync with what "this week" means elsewhere), a **login-streak calendar** (`loginStreak.recentDates`, a capped-at-7 rolling array added alongside the existing `streak` counter, not a replacement for it), an **anniversary line** (`careerStats.firstPlayedDate`, set once on the very first completed run, never touched again), and a **mutator-exploration nudge** as a 5th spotlight mode (`settings.mutatorsEverEnabled`, recorded in ONE place — the Play button's click handler, where every mutator flag is already read for real — rather than editing all ~15 individual mutator checkboxes; deliberately excludes `dailyChallenge` since that's a distinct system already promoted via its own daily-reset spotlight mode, not a "try this mutator" pick). `MUTATOR_LABEL_KEYS` (`Game.js`) was renamed/extended from the older `WEEKLY_FEATURED_MUTATOR_LABEL_KEYS` (which only covered the 8 `WEEKLY_FEATURED_MUTATORS`) to cover all 14 non-daily mutators, rather than adding a second near-duplicate label map. Also fixed a real duplicate-audit catch mid-build: the Nearly There nudge was asked to show "top 3" closest achievements, but this codebase only has 2 achievements with genuinely persistent numeric backing (`NEARLY_THERE_CANDIDATES`, see its own comment) — everything else is a per-run counter that resets, so showing "progress" toward those would be actively misleading. Shipped showing however many honestly qualify (0-2) rather than padding to a number that doesn't reflect what's actually trackable.

A third round (round 4) added, after auditing for and deliberately skipping the riskier asks (mid-run save/resume, server-side anti-cheat, a social-infra bundle of friend-challenges/clans/activity-feed/presence, and chat/messaging - all flagged as needing real new cost/scope/moderation before building): **achievement unlock hints** (`hintKey` field added to every `ACHIEVEMENTS` entry, shown in the Achievements panel instead of a bare `"???"`), a **region filter** on the leaderboard (`settings.region`, one of 6 values, `region` field on leaderboard docs is *omitted entirely* when unset rather than defaulted to a region - the security rule's enum check only applies when the field is present at all), an **achievement-count leaderboard** (same `leaderboard` collection, new `achievementCount` field, sorted differently - not a separate collection), a **global average comparison** and **percentile ranking** (both via Firestore's `getCountFromServer`/`getAggregateFromServer` aggregations, never a client-side download-and-average), a **live-subscribed leaderboard** (`CloudSync.subscribeTopLeaderboard`/`onSnapshot`, subscribed only while the Cloud Save panel is actually open and unsubscribed on close/sign-out to keep the read cost bounded), a **"Most Improved" badge** (just a label on the weekly leaderboard's #1 entry - that ranking already *is* "most improved this week" by the same measure, no new metric needed), **"Today" session stats** (`_sessionKills`/`_sessionStartTime`, deliberately session-local only, reset every page load, never persisted - distinct from careerStats' lifetime totals), a **Best Run breakdown card** and **favorite-difficulty line** (both pure-derived from data already tracked - `runHistory`'s difficulty/loadout/companion fields and `careerStats.difficultyStats`, no new tracking), **avatar frame tiers** (automatic border-color escalation off the same 1-5 tier index the avatar-level badge already computes, not a picker), a **custom Player Title color** (`settings.titleColor`, applied via `style.setProperty('color', ..., 'important')` since `.menu-best-stats`'s own color rule is itself `!important`), a **detailed Achievement Showcase style** (stacks the 3 slots into a column of two-line cards instead of the compact row, since 3 full achievement names side by side would overflow the 290px right column), a **companion color preview swatch**, **Large Text Mode** (CSS `zoom` scoped to `#menu` + every modal panel - *not* a root `font-size` bump, since almost all sizing here is fixed px, not rem; deliberately does not touch in-game HUD text, which already has its own HUD Scale slider for exactly that), **High Contrast Mode** (a `filter: contrast()/saturate()` on `#app`, works during gameplay too), a persistent **Keybind Cheat Sheet** HUD toggle (distinct from the one-time tutorial toasts and the replayable How to Play modal), **sound test buttons** next to the volume sliders, a **structured, dated changelog list** in Credits (replacing the old single static paragraph), and **standalone trivia facts** as a 6th spotlight mode (distinct from `SPOTLIGHT_TIPS` - actionable advice vs. pure lore flavor).

**Gotcha**: a single `getAggregateFromServer(coll, { avgKills: average('bestKills'), avgNight: average('bestNight') })` call - averaging two different fields in one aggregate query - triggered `failed-precondition: The query requires an index`. Splitting it into two separate single-field aggregate calls (`Promise.all([...average('bestKills')..., ...average('bestNight')...])`) needs no index at all and returns the same data. If a future aggregate query ever demands an index, try splitting fields into separate calls before assuming a Firestore Console index (or a paid-plan limitation) is actually required - it often isn't.

**Chat** (2026-08-27) - the "chat/messaging" item flagged as skipped above eventually got built, once moderation was actually decided (no word filter, client-side spam mute only - see the design conversation). Splits across **two completely different transports**, which matters for anyone touching it: Global chat (`globalChat/{messageId}`) and Clan chat (`clans/{clanId}/messages/{messageId}`) are plain Firestore collections, same pattern as everything else (`CloudSync.sendGlobalChatMessage`/`subscribeGlobalChat`, `sendClanChatMessage`/`subscribeClanChat` - `onSnapshot`, capped history, subscribed only while the chat panel is actually open). **Party chat is not Firestore at all** - a multiplayer session's players aren't Firebase-Auth-signed-in (see the Realtime Database section above - `Multiplayer.js`/`api/multiplayer/*.js` mint their own random `playerId`, no Firebase Auth involved), so party messages piggyback on the existing 100ms position-sync poll (`api/multiplayer/sync.js`'s `chatText`/`chatNickname` request fields, `chat` response field) instead - same broadcast-and-TTL-prune shape as `worldEvents` in that file, just a 10-minute TTL instead of 15 seconds since chat is meant to read as real scrollback, not a one-shot trigger. The client dedupes party messages by id (`_chatPartySeenIds`) the same way it already dedupes world events. Rate-limiting (5+ messages in 10s → 5-minute mute) is enforced **client-side only** in all three channels - there's no custom backend here to enforce it server-side (same trust model as everything else, see the anti-cheat note above), so a modified client could bypass it; the Firestore security rules only enforce message shape/length, not timing. The keydown-suppression-while-typing fix (letters typed into the chat input no longer also trigger gameplay hotkeys) reused the exact capture-phase `stopImmediatePropagation()` technique documented in the Menu redesign notes below for the mouse-parallax fix - same reasoning, different listener.

- **Cloud Save is a three-way merge, not an upload (since 2026-09-28).** `CloudSaveUI.syncWithCloud` reads the cloud, merges it with this device's data against `localStorage['gayz-cloud-base']` (the content this device last agreed with the cloud on) using `CloudMerge.mergeSaves`, and uploads with a Firestore compare-and-set transaction (`CloudSync.pushCloudSaveIfUnchanged`) - never a blind `setDoc` over the save. The old blind upload, fired every ~30s by the settings autosave, let any idle device overwrite newer progress from another device (real report: stats differed between iPad/iPhone and the main PC). Rules that bite if broken: only `gayz-*` keys sync (`isSyncedKey` - Firebase's own `__sak`/auth keys must never be uploaded or tracked); per-device keys go in `DEVICE_ONLY_KEYS`; a new *totals/balance* storage key needs adding to `ADDITIVE_KEYS` or two devices' changes to it won't add up; incoming changes are pulled **once, before the game is built** (`CloudPreBoot.js`, run from `main.js` alongside the model preloads, capped at 6s, only on devices that have synced before) - it merges into localStorage and sets the base to the exact cloud content (not the merged result, so this device's unuploaded changes still get uploaded, and counted once). After boot, **every automatic sync is upload-only** (`allowApply: false` - it uploads the merge and sets the base to this device's current content, never writes other devices' data into the running page); only explicit clicks (Sign In, Sync Now, the conflict prompt) may apply-and-reload. Letting automatic syncs reload caused a reload loop reported twice on 2026-09-28 (a 20s cooldown guard alone didn't fix it) - don't reintroduce an automatic apply. **A device without a base never wins a conflict** (`mergeSaves` forces `preferLocal` off when `base` is null, 2026-09-30): such a device just generated a random Player ID and `Survivor####` name, and since its writes always look newest it used to overwrite the account's real ID/name in the cloud (coins survived, merging by max) - reported as "I got a new ID and name". The pre-boot pull also runs when localStorage has no `gayz-cloud-last-sync` but Firebase still has a signed-in session in IndexedDB (`hasStoredFirebaseSession`, reads `firebaseLocalStorageDb` directly without loading Firebase and without creating the database), so a device whose localStorage was cleared boots with the account's data instead of a fresh identity. A module that reads localStorage at import time (like `Keybinds.js`) needs a re-read after the pre-boot pull (`reloadBindings()` in `main.js`). Test seam for the pre-boot pull: `window.__cloudPreBootBackendForTests = { getUid, fetchCloudSave }` set via `addInitScript`. Test harness: set `game.__cloudBackendForTests = { fetchCloudSave, pushCloudSaveIfUnchanged }` to run the real flow against an in-memory fake cloud across two browser contexts.

- **Every persisted stat is untrusted the instant Import Save exists.** `_importSaveFile` (Local Sharing batch) writes an uploaded file's contents into localStorage wholesale, so any field previously safe to interpolate raw into `innerHTML` because "it's always a number, this game itself only ever writes numbers here" no longer holds — a crafted save file can put a string there instead. `_safeStatNumber(v)` (coerces to a finite number, defined next to `_escapeHtml` in `Game.js`) and `_escapeHtml` are the two fixes; a security review caught 2 call sites on the Local Sharing batch's own new UI, and auditing the same pattern found 6 more in already-existing leaderboard/history renders (`_updateLeaderboardDisplay`, `_updateBossRushLeaderboardDisplay`, `_updateHouseholdLeaderboardDisplay`, `_updateHardcoreMemorialDisplay`, `_renderDailyLeaderboard`, the Run History list, the Profile stat grid) that had been safe until that same batch made them reachable from an untrusted file. Apply both defensively to any *new* code that renders a persisted field via `innerHTML` — treat "this value came from `this.xStats`/`this.xLeaderboard`/anything loaded via a `loadX()` function" as no safer than raw user input now, not just nickname-shaped fields.

- `_showLoreToast(text)` silently no-ops via `if (!this.gameStarted) return` — it only shows anything once the player has clicked Play. Any toast meant to fire from homepage-only code (sign-in, Profile/Friends/Cloud Save panel actions, anything reachable before a run starts) needs `_showHomepageToast(text)` instead, or it will call cleanly, change nothing visibly, and look like the feature does nothing. Bit a real fix 2026-09-26 (the cloud-save-restore-failure toast below was written with `_showLoreToast` first, verified as a no-op via a live test, then corrected) - test any *new* toast call from a homepage-reachable code path by checking `game.gameStarted` at the point it fires, not just by reading the call site.

- **Cloud Save's restore-on-sign-in path (`Game.js`'s `_afterCloudSignIn`) had no error handling around `CloudSync.fetchCloudSave` at all until 2026-09-26** - a genuine thrown exception (a real network hiccup, not a clean "no document") propagated straight out of the whole function, silently skipping both the pull-and-apply branch and the first-time-push branch. Real-world effect (an actual report): signing into the same account on a new device showed a totally different name/Player ID/stats instead of the real synced save - sign-in itself still succeeded, so it looked normal, but the save was simply never restored, with nothing telling the player anything had gone wrong. Fixed by wrapping each retry attempt individually and tracking "a fetch actually failed" separately from "a fetch cleanly returned no document" - only the latter is trusted as a genuine first-time sign-in. Any *other* Firestore read added to a sign-in/restore-type flow needs the same three-way handling (success / confirmed-empty / failed-with-retries-exhausted), not a bare `if (!result)` that conflates the last two.
- **Playing offline (2026-10-17, Gaymi: "if their offline with no internet they can play fully and do everything thats single player like design a skin everything offline").** No "offline mode": the whole site works offline after one online visit. *Service worker:* `src/sw.js` is a template (never imported by the bundle); `vite.config.js`'s `serviceWorkerPlugin` writes `dist/sw.js` on `closeBundle` with `BUILD = { version: buildId, files }` - every file in dist except `SW_SKIP` (legacy bundles, benchmark, version.json, txt/map/LICENSE, and the old Map 1 leftovers still in public/: `models/{buildings,props,humans,titan,zombie}/`, `textures/` - ~18 MB kept). Install caches them all into `gayz-<buildId>` (8 at a time, `cache: 'reload'`, one failure never stops the rest) then `skipWaiting`; activate deletes all but the newest older `gayz-*` cache (an open tab of the previous build can still load its lazy chunks) and claims. Fetch: same-origin only; navigations network-first with a 4 s timeout, offline falling back to the exact path, then `/index.html` / `/` (panel URLs work like the vercel.json rewrite); other GETs cache-first (this build, then older), else network + cached; `/api/*`, `version.json`, `sw.js` always network. `vercel.json` serves `/sw.js` with `no-cache`. *Registration:* `Offline.registerServiceWorker()` from main.js - production only, and not in automated browsers (`navigator.webdriver`) unless `localStorage['gayz-sw-in-tests']` is set (tests/offline.spec.js does), since it downloads the whole game per browser context. *No outside files any more:* the fonts are self-hosted in `public/fonts/` (`fonts.css` + woff2, same unicode-range splits Google serves, OFL licences in `LICENSE.txt`), and Design a Skin's import map points at `/skin-designer/three/` - three.module.min.js, three.core.min.js and OrbitControls.js copied from node_modules (same three version as the game) by the same plugin (and served from node_modules by its dev-server middleware). *Game side:* `Offline.installOfflineGuards(game)` (main.js): `html.is-offline` while offline (`src/offline.css` dims `ONLINE_ONLY`), a capture-phase click guard on `ONLINE_ONLY` (Global, Friends, Clan, Market, Gallery, inventory Sell, every sign-in button, Cloud Save sign-in/sync, chat send - Enter in the chat inputs too - and the editor's Share Map / Community Maps / Post to Gallery / Build Together) that shows `needsInternet` instead; toasts `offlineNow` / `backOnline`. `GalleryUI.openGallery`/`startSkinPost` also check (`blockedOffline`) for routes and Design a Skin's Post to Gallery. `CloudPreBoot` skips the boot-time cloud pull when `navigator.onLine === false` (it would wait out its timeout). **Rule: anything single player must keep working offline - load files from the game itself (no CDN), and add a new online-only button to `ONLINE_ONLY` (and `offline.css`).** Test: tests/offline.spec.js "the game plays offline after one online visit" (Playwright `context.setOffline(true)`).

- **Offline detection checks for itself (2026-10-17).** `tests/offline.spec.js` failed on main: after `context.setOffline(true)` the page (served by the service worker) still had `navigator.onLine === true`, so `is-offline` was never set - the same thing real players get on Wi-Fi with no internet. `Offline.js` now also probes `/version.json` (`cache: 'no-store'`, never answered from the SW cache, `PROBE_TIMEOUT_MS` 8s): a fetch that throws (can't reach the server) sets `unreachable`, a 404/500 still counts as online (so the dev server is fine). - **Sign-in providers (2026-10-23).** Google, Steam, GitHub, Discord (Gaymi dropped Microsoft, Facebook, LINE, Apple and WeChat - phone number, card or company needed). `CloudSync.signIn(provider)`: Google and GitHub are Firebase popups - GitHub's OAuth app (owner mrgulper, callback `https://gayz-aa69c.firebaseapp.com/__/auth/handler`) has its ID/secret stored in Firebase Console -> Authentication -> Sign-in method, never in code. Discord and Steam aren't Firebase providers: `signInViaServer` opens `/api/auth/<provider>` (`api/auth/[provider].js` + `api/_lib/oauth.js`) in a small window **straight from the click, before any await** (or the browser blocks it). The server sets a random state cookie, sends the player to the site, checks the answer (Steam: OpenID 2.0 `check_authentication` plus return_to/op_endpoint/claimed_id checks; no key needed, name/picture from the public `?xml=1` profile), creates/updates the Firebase user `<provider><id>` (letters+digits only so `api/_lib/servers.js` `validId` accepts it) with firebase-admin, and ends on a page that hands back a custom token by postMessage **and** BroadcastChannel (a site's COOP header can cut `window.opener`; for the same reason `popup.closed` can read true early, so "closed" only counts after the game window gets focus back and 3s pass). Discord keys are Vercel env vars `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET` (Production; redirect `https://gayz.vercel.app/api/auth/discord`); a missing key shows `authNotReady`. Different sites = different accounts (different uid, different Cloud Save); Firebase's "one account per email" makes a same-email second site fail with `account-exists-with-different-credential` -> `authOtherMethod` toast. Closing the window is silent; sign-in errors use `_showHomepageToast`. Tests: "auth: Discord/Steam sign-in checks" in `tests/servers.spec.js`.
